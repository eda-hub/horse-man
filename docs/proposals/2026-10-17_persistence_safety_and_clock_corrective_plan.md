## 4. 書込み経路の是正設計

### 4.1 開始時に許可範囲を明確にし、実経路を確認する

1. repository、既存日次branch、head SHA、作業対象path、操作種別、利用者の依頼とAGENTSに基づく書込み範囲を固定する。予想保存依頼の範囲内で反復確認を要求しない。
2. mainを読む経路と日次branchへ書く経路を分け、利用可能なGitHub連携の能力を確認する。権限の取得や設定変更を黙って追加しない。
3. 実依頼がある場合、予想作成前に必要な正式intentそのものを通常経路で保存・読戻しする。これを最初の実書込み確認にし、ダミー予想・ダミーreceipt・架空の事前証跡は作らない。
4. 事前の検証は専用の試験branchと明示的な合成データで行う。正式日次記録・KPIへ混ぜない。試験branchへの成功と、当日利用経路への成功は別々に記録する。
5. 同じbranchのcreate/updateと返却commitからの読戻しに成功した場合だけ、そのセッションの経路確認済みとする。read成功・branch作成成功・別日の成功だけで書込み可能と断定しない。

### 4.2 証拠を残して拒否を分類する

予定の追加モジュール `scripts/prediction_persistence_io.py` と操作アダプターで、次を要求ごとに記録する。ツールが実行前に拒否した場合はAPI未到達を区別する。取得できない値はnullと理由を残し、拒否を再現するために危険な要求を作らない。

- 操作ID、試行番号、repository/branch/path、expected head/file SHA、固定bytesのSHA-256。
- 正確なツール/経路名、操作種別、要求/応答の時刻と所要時間、API到達の有無。
- 拒否主体・エラー種別・HTTP状態・request ID・再試行可否・理由の原文（認証情報等は除去）。安全性審査の表示をGitHubのエラーとして書き換えない。
- 保存状態、読戻し状態、時刻判定、個別完了を独立保持する。ログ出力自体が失敗した場合も利用者へその不足を伝える。
- 日次branchへ書けない間は、固定bytesと障害記録を実行環境に保持し、リモート保存未完了と伝える。GitHub保存と同じ耐久性があるとは扱わない。
- 復旧後の障害記録は `docs/validation/persistence-incidents/YYYY-MM-DD/` に追記し、当時の正式receiptの代用にしない。秘密を含む原文は公開リポジトリへ送らず、秘匿箇所と欠落理由だけを記録する。

| 分類 | 必要な根拠 | 処置 |
|---|---|---|
| 実行環境/ツールの安全性拒否 | 実際の拒否文と操作。HTTP未到達も記録 | 拒否された操作を停止し、理由と対象を提示。経路/資格情報の付替えで同じ操作を通さない。理由に適合する実質的に安全な限定操作がある場合だけ再評価 |
| 認証・GitHub権限/branch制約 | サービス応答、取得できる範囲の設定 | 不足の範囲を特定し、必要な接続/権限修正を案内。上位権限要求やmain書込みへ変更しない |
| 競合・古いSHA | 最新head/file内容と要求SHA | 再取得して同一性確認。一致済みなら重複書込みなし、不一致なら履歴を保持して競合解消。force/resetを行わない |
| 通信・timeout・一時障害 | 実際の応答と到達状態 | まずremoteの同一bytes/commit有無を読取り確認。未反映を確認した場合だけ、締切内・既存上限で同bytes再保存 |
| CI/個別検査の不合格 | run/jobまたはchecker出力 | 本体保存の事実を保持し不足を修正。CIを無効化せず、保存拒否と呼ばない |
| 理由不明 | 根拠不足そのもの | 不明と記録。安全性拒否の可能性が解消するまで、別経路の同操作再試行をしない |

最大2回の再保存は一時障害・整合済み競合の復旧に適用し、安全性拒否を反復する許可ではない。APIのupdateは現在のblob SHAを指定し、ref操作が必要な実装では最新headを照合して非強制更新に限定する。応答を失った場合は保存済みを先に探索し、正式固定内容を新しい予想へ作り直さない。

## 5. 時刻判断の是正設計

### 5.1 時計と発走根拠を共通処理へ集約

新規 `scripts/prediction_clock.py` を予定する。判定APIは対象race、公式発走根拠/既存変更履歴、観測時計を受け、判定値・残秒・理由を返す。chat側の自然文や時刻文字列の大小比較を判断元にしない。

- 現在時計は判断直前に実行環境/利用可能な時計ツールから取得するUTCの日時。JSTへ変換して保存・表示する。日付・オフセットのない値を受理しない。
- 発走予定は開催日・場・Rの一致する公式scope/根拠と既存の公式発走改訂chainから得る。別raceの時刻、開始時刻、回答時刻、オッズ更新時刻を代用しない。
- `task_started_at`、`clock_observed_at`、`decision_at`、`data_cutoff`、`fixed_at`、`write_requested_at`、`write_completed_at`、`body_readback_at`、`receipt_readback_at` を役割別に保持する。取得不能はnullと理由。サーバ時刻と端末時計を区別する。
- 比較はtimezone付き日時をUTCへ正規化して行い、`remaining_seconds = scheduled_post - decision_at` を機械計算する。`remaining_seconds > 0` が発走予定前、0以下は予定時刻到達。予定到達を実際の発走確認済みとは表現しない。
- 時計が欠測・矛盾・古い場合は未判定にし、「発走後」へ変換しない。固定内容は保全する。

### 5.2 時計の鮮度・境界・読み戻し

運用初期の提案値として、判定用の時計は観測から5秒以内を要求し、保存要求直前に再取得する。時計観測の経過はmonotonic時計で測る。取得・比較中の経過を足して判定し、時計の巻戻り/飛びやmonotonicとの2秒超の乖離を検出したら未判定と再取得にする。これらの値は固定テストで検証し、隠れた猶予や締切延長に使わない。

時計の分解能、取得遅延、同期状態により発走境界の前後を確定できない場合は、確定可能な時刻範囲を保持して未判定とする。分単位しか得られない時計を秒精度へ捏造しない。サーバ時刻との照合が可能ならずれを記録するが、HTTP応答のDateやcommitの自己申告日時を原本保存・読戻し時刻の証明に流用しない。

1. 正式intentを保存・読戻ししてから予想を作る。FIX後に事前宣言を挿入して順序を整えない。
2. 固定・独立FIX保存・本体保存の直前に時計を取り直し、同じ原本bytesと対象を確認して処理する。補助情報待ちで保存時間を消費しない。
3. 本体読戻し直後に時計を取得し、commit/path/hashの一致と実際の発走境界を検査する。続くreceiptも保存・読戻しを検査する。
4. 書込要求が発走前でも読戻しが発走予定以後なら前向き適格にしない。同時刻も不適格。時刻未判定は未認証として保全する。
5. 保存の成否、発走前かどうか、宣言→FIX→本体→receiptの順序、正式KPIの可否を別項目で返す。現在の監査時計がレース後であるだけで、過去の発走前保存を発走後保存に変えない。
6. 回答の「発走予定前/予定到達/時刻未確認」と残時間は同じ処理結果から生成する。自然文が判定と矛盾したら検出し、予想提示と固定内容の保全は継続しながら、誤った断定を出力しない。

| readback不一致、誤branch、main、パス逸脱 | 完了拒否。指定リポジトリ・branch・pathの範囲を維持 |
| CI失敗、checker失敗、推奨未完了 | 本体保存と独立表示。監査を緩めたり予想保存を破棄したりしない |
| ログに秘密、ログ保存失敗 | 秘密を公開しない。ログ欠落を検出し調査完了としない |
