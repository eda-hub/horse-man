# 競馬予想運用の不正確さに対する是正処置 — 検討企画書

- 作成日：2026-09-20
- 状態：**検討企画・未実施**
- 対象：チャットで行うProduction予想、最終予想、買い目確定、実購入記録、結果後回顧
- 参照ルール：v1.6.1
- 参照事例：2026-09-20 JRA全体選別・個別最終予想・回顧
- 関連PR：#34
- **本書は実行ルールの正本ではなく、是正処置を検討するための企画書である。**
- 本書だけを根拠に現行Production、Shadow、KPI適格条件、購入ルールを変更しない。
- 実施する場合は、Ownerモジュールを分けて別途正式変更する。サイクル途中の結果を理由に既存予想ロジックを遡及変更しない。

## 1. 目的

2026-09-20に発生した問題は、主として予想理論そのものではなく、

- 発走前snapshotの識別・保存内容が不十分
- 既存Productionを再利用すべき場面で再生成
- 初期→最終の差分理由が追跡できない
- 購入前監査の実施結果が記録されない
- 推奨買い目とユーザー実購入の状態を混同
- 回顧時に全体選別対象の転記が不完全
- Production / Betting / ShadowのKPI適格性を一括判定
- 結果後に判明した材料と発走前根拠の境界が曖昧

という**運用面の不正確さ**から生じた。

本企画の目的は、予想ロジックを大きく変更せず、チャット実行の各段階に最低限の状態管理・完了条件・参照関係を設け、同種事故を再発しにくくすることである。

## 2. 今回確認された事象

| 分類 | 2026-09-20に確認された事象 | 問題の本質 |
|---|---|---|
| 対象管理 | 全体選別16Rのうち、回顧当初は個別最終5R中心の記録になった | prediction_scope と永続記録の照合不足 |
| 基準予想識別 | baseline_forecast_id を発走前に確認できない | 「どのProductionを再利用するか」の参照キー不足 |
| Production再利用 | 中山9R・阪神10Rで既存初期Productionがあったのに「snapshotなし」と扱った | 既存状態の探索・参照失敗 |
| 差分更新 | 阪神7R、オールカマー等で順位・確信度変更の理由が完全に追跡できない | before / after / reason / time の不足 |
| 購入ルール | 中山9Rで▲9の単勝を固定案へ採用 | 35.2の実行監査漏れ |
| 依存監査 | 70〜100%の馬依存案があるが、48.2のレンジ下側・監査後判断を追跡できない | 監査の「実施」と「判断への接続」が見えない |
| 実購入帳簿 | 阪神7Rは購入案と購入完了を区別できなかった | recommendation / intent / confirmed purchase の状態混同 |
| KPI判定 | 一時的にShadow欠落とProduction適格性を一括して扱った | KPI単位の独立判定不足 |
| 証拠時点 | 結果後コメントやローテ仮説が回顧文中で事前根拠に近い扱いになった | PRE_RACE / POST_RESULT の出所境界不足 |
| 参照時刻 | チャットUIの厳密な投稿時刻を後から復元しにくい | snapshot内部に時刻を保持していない |

## 3. 根本原因の仮説

### 3.1 ルール不足より「実行状態」の不足

現行manualには、

- Production / Shadow分離
- baseline_forecast_id
- 同一レースProduction再利用
- 差分更新
- 単勝は原則◎
- 48.2万能軸監査
- 回顧時の全対象記録
- KPI別適格判定

など、今回必要だった原則の多くがすでに存在する。

したがって、単純にルールをさらに追加しても、実行時に「今どこまで完了しているか」を追跡できなければ再発する可能性が高い。

本企画では、**判断ルールを増やす前に、実行状態を明示し、次工程へ進む条件を固定する**ことを主な是正方向とする。

### 3.2 自由文だけでは工程境界が消える

チャットの自然文回答だけで、

- 初期Production
- 最終Production
- 価格照会
- 買い目固定
- Shadow
- 実購入
- 結果後回顧

を扱うと、同じレースの複数時点が混ざりやすい。

各回答に「これはどの状態のsnapshotか」を示す小さな構造化ヘッダが必要と考える。

### 3.3 「確認したつもり」を防ぐ完了条件が弱い

たとえば48.2は存在していても、

- 馬依存率だけ出した
- 高いと認識した
- しかしレンジ下側や軸崩れシナリオを確認していない
- 最終配分へどう反映したか残っていない

場合、監査が完了したのか判定できない。

今後は監査を**項目列挙ではなく完了条件**として扱う必要がある。

## 4. 是正方針

是正処置を6つの工程に分ける。

1. **全体選別snapshotの完全性**
2. **Production識別と差分更新**
3. **購入前監査の完了ゲート**
4. **実購入状態の明確化**
5. **回顧転記の完全性**
6. **KPI適格性の独立判定**

各工程で「最低限保存するもの」「次工程へ進める条件」「失敗時の扱い」を決める。

## 5. 是正案A — 発走前snapshotヘッダ

### 5.1 狙い

チャット回答そのものを後から一意に参照できるようにする。

### 5.2 提案する最低項目

全体選別・個別予想・最終予想では、回答の末尾または表内に次を保持する。

| 項目 | 内容 |
|---|---|
| snapshot_type | WHOLE_DAY / INITIAL_PRODUCTION / FINAL_PRODUCTION / BETTING_FIXED / SHADOW |
| race_id | 日付・場・Rを一意に識別 |
| baseline_forecast_id | 同一Production系列を追跡するID |
| manual_release | v1.6.1等 |
| snapshot_at_jst | チャット内に明示する固定時刻 |
| information_cutoff_jst | 使用した動的情報の締切 |
| market_used_for_ability | 必ず false / 未確認等を明示 |
| bodyweight_status | JRA取得 / fallback / 未取得 |
| production_status | NEW / REUSED / UPDATED |
| previous_snapshot_ref | 更新時だけ直前snapshotを参照 |

### 5.3 IDの扱い

IDは結果後に作らない。

方式は実施時にOwnerで確定するが、候補として、

> race_id + manual_release + initial fixed timestamp

から作る人間可読なIDを検討する。

例：

> 20260920-NAK09-v1.6.1-1203

ただし命名規則そのものは本企画では正式化しない。

### 5.4 全体選別時の完全性

モード2で16Rを対象にしたなら、16R全てについて最低限、

- race_id
- ◎〜上位候補
- 勝率等のProduction確率
- 予想確信度
- 選別区分
- 購入優先度
- baseline_forecast_id

を1行以上残す。

**購入優先上位5外は見送りではない。**

上位5は「最終検討対象」であって、6位以下の買い / 見送り判定は別フィールドで管理する。

## 6. 是正案B — Production差分更新ゲート

### 6.1 狙い

同一レースを再予想するとき、既存Productionを見失ってゼロから再生成しない。

### 6.2 最終予想開始時の確認

最終予想に入る前に、必ず次の順で確認する。

1. race_id一致
2. manual_release一致
3. baseline_forecast_idの存在
4. 初期Production順位・確率・確信度
5. 初期時点の馬場等、既に織り込み済みの動的情報
6. 新たに追加された非価格情報

### 6.3 差分表

順位・確率・確信度を変更する場合、最低限次を残す。

| 対象 | Before | After | 非価格理由 | 新情報か再解釈か | 証拠強度 | 情報時刻 |
|---|---|---|---|---|---|---|

重要なのは、**「理由がある」だけではなく、その理由が初期予想後に新しく発生した情報なのか、以前からあった情報の再解釈なのかを分ける**ことである。

静的情報の再解釈だけで順位を大きく変える場合は、なぜ初期評価が変わったかを明記する。

### 6.4 既存snapshotを取得できない場合

今後、

> 既存snapshotが見つからないので再生成する

ことを自動的に許可しない。

候補対応：

- チャット文脈に明示された既存順位がある場合は、それを再利用する。
- baseline IDだけ不明なら「ID未確認」とし、新IDを勝手に発行しない。
- 順位自体が取得できない場合は BASELINE_LOOKUP_FAILED とし、再生成した案を既存Productionの正式更新として扱わない。
- 締切が迫る場合はfail-softで、取得できた既存情報を維持したまま動的情報だけ報告する。

## 7. 是正案C — 購入前4ゲート

購入案をユーザーへ出す前に、次の4ゲートを通す。

### Gate 1：券種適合

- 単勝対象は◎か
- 馬連 / ワイドの自然な本線が欠けていないか
- 券種が予想シナリオと整合しているか

中山9Rの▲単勝はここで停止できる。

### Gate 2：価格

各買い目について、

- 使用オッズ
- 取得時刻
- 的中成立に必要な確率
- 自分の推定成立確率
- 合理的レンジ
- レンジ下側
- 買い条件との余裕

を確認する。

複数馬券では、単純な各馬勝率ではなく**券種成立確率**として扱う。

### Gate 3：馬依存

最大馬依存率を算出する。

ただし70%・100%を一律禁止しない。

高依存でも、

- 依存馬が崩れる独立シナリオが小さい
- レンジ下側でも期待値が維持
- 縦目が独立して期待値負
- 集中の理由を説明可能

なら維持を許容する。

重要なのは**依存率を出した後の判断**を保存すること。

### Gate 4：監査後の最終判断

最後に必ず、

- 維持
- 配分変更
- 総投資削減
- 見送り

のいずれかを記録し、1〜2文で理由を付ける。

この最終判断がなければ、48.2監査は「実施済み」としない。

## 8. 是正案D — 実購入状態の3段階化

推奨と実購入を混同しないため、状態を分ける。

| 状態 | 意味 | 実購入帳簿 |
|---|---|---|
| RECOMMENDED | アシスタントが買い目を提示 | 算入しない |
| INTENDED | ユーザーが「これを買う」等の意思を表明したが、購入完了は未確認 | 算入しない |
| PURCHASE_CONFIRMED | ユーザーが「買いました」「購入しました」または実購入一覧を提示 | 算入する |

金額・買い目が曖昧なら推測で補わない。

これにより、阪神7Rのような「1,500円条件の買い目提案」を購入済みとして誤計上することを防ぐ。

## 9. 是正案E — 回顧開始時の取り込み台帳

回顧を始めるとき、結果を見る前後の診断より先に「発走前記録を取り込む工程」を置く。

### 9.1 回顧入力台帳

最初に次を作る。

| race_id | 初期Production | 最終Production | Betting固定 | Shadow | 実購入確認 | 結果 |
|---|---|---|---|---|---|---|

この時点で prediction_scope_count と行数を照合する。

### 9.2 完了条件

- 全体選別16Rなら16行ある
- 各行は「確認済み / 未確認」を持つ
- 未確認を「見送り」「非該当」に置換しない
- 結果から欠損した印・確率・Shadowを再構成しない
- 個別最終5Rだけ詳細がある場合でも、残り11Rの存在を消さない

### 9.3 証拠時点タグ

回顧で使う材料を、

- PRE_RACE_RECORDED
- PRE_RACE_AVAILABLE_BUT_NOT_RECORDED
- POST_RESULT_NEW

に分ける。

POST_RESULT_NEW は次回仮説の候補にはできるが、今回の事前判断理由には使わない。

## 10. 是正案F — KPI適格性マトリクス

KPIはレース単位で一括して「適格 / 不適格」としない。

### 10.1 独立判定

現行の正式Production予想精度KPIは、validation READMEで定義された必須条件一式を維持する。順位だけ、確率だけを切り出して正式適格化する変更は本企画では行わない。

そのうえで、**Production / Betting / 各Shadowを相互に巻き込んで一括除外しない**ことを徹底する。

| KPI系統 | 主な必須条件 | 他KPI欠落の影響 |
|---|---|---|
| Production予想精度 | 現行validation READMEの必須条件一式：baseline ID、レース・時刻、順位・印・確率、予想確信度、当日馬体重取得状態等 | Betting / Shadow欠落では除外しない |
| Betting ROI | Production適格＋買い/見送り判定＋使用価格・時刻＋固定10,000円案等 | Shadow欠落では除外しない |
| 51B | 発走前51B固定 | Productionが適格でも51B欠落なら51Bだけ除外 |
| E-09 | 発走前E-09固定 | 同上 |
| E-11/E-12 | Production買い目固定後の発走前比較案 | Production ROIとは別 |
| E-13 | P/A/Bの同一入力・発走前固定 | E-13欠落はProductionを落とさない |

順位捕捉、確率校正、買い目接続等は**原因診断の内訳**として分けて見るが、現行の正式適格条件を分割・緩和しない。

### 10.2 判定履歴

適格性を後から修正する場合、

- 変更前
- 変更後
- 転記漏れだった発走前証拠
- 変更日時

を残す。

結果後に新しい値を作って適格化しない。

## 11. 運用上の状態遷移

チャット実行を次の状態として扱う案を検討する。

    S0 対象登録
     ↓
    S1 INITIAL_PRODUCTION_FIXED
     ↓
    S2 DYNAMIC_INFO_UPDATED
     ↓
    S3 FINAL_PRODUCTION_FIXED
     ↓
    S4 BETTING_AUDIT_COMPLETE
     ↓
    S5 BETTING_FIXED
     ↓
    S6 SHADOW_COMPLETE / SHADOW_PARTIAL
     ↓
    S7 USER_PURCHASE_STATE_RECORDED
     ↓
    S8 RESULT_REVIEW_INGESTED
     ↓
    S9 REVIEW_COMPLETED

各状態は前状態の参照を持つ。

例外：

- Shadow未完了でも、Productionは発走前に提示できる。
- ただしShadow状態を「未完了」と明示する。
- 発走後にS3以前を作り直さない。

## 12. 運用エラーコード案

自然文だけでなく、回顧で検索しやすい識別子を持つ案。

| コード案 | 意味 |
|---|---|
| BASELINE_ID_MISSING | 発走前baseline ID未固定 |
| BASELINE_LOOKUP_FAILED | 既存Productionを取得できない |
| UNJUSTIFIED_PRODUCTION_CHANGE | 差分理由・時刻・証拠が不足 |
| SINGLE_WIN_MARK_MISMATCH | 単勝対象が◎でない |
| BETTING_AUDIT_INCOMPLETE | 48.2等の購入前監査が未完了 |
| PURCHASE_STATUS_AMBIGUOUS | 購入案と購入済みを確定できない |
| REVIEW_SCOPE_MISMATCH | 事前対象数と回顧行数が不一致 |
| KPI_ELIGIBILITY_COUPLED | 独立KPIを一括除外した |
| POST_RESULT_EVIDENCE_BACKFLOW | 結果後材料を事前根拠へ混入 |
| MARKET_INDEPENDENCE_UNVERIFIED | 市場照会前の能力snapshotを確認できない |

正式なコード名称・Ownerは実施時に決める。

## 13. 直近サイクルでの試行案

第2サイクルは継続中のため、ここでProduction判断ルールを変更しない。

もし残りの9/21・9/22で本案を試す場合は、**運用記録の完全性だけを確認するドライラン**に限定する案が妥当。

ドライランで確認するもの：

- baseline IDが発走前に残ったか
- 全体選別なら対象全Rが1行あるか
- 最終更新が差分形式になったか
- 単勝・48.2監査の完了状態が残ったか
- Shadow完了 / 未完了がProductionと分離されたか
- 実購入状態を誤計上しなかったか
- 回顧時に全対象を再取得できたか

**予想精度が良くなったかをこの2日だけで本案の採否判断に使わない。**

## 14. 実施フェーズ案

### Phase 0 — 企画確認

本書の内容をレビューし、

- 実行状態を明示する方向でよいか
- チャット出力が冗長になりすぎないか
- baseline ID方式
- 購入監査の必須項目
- エラーコード

を確定する。

### Phase 1 — サイクル中ドライラン

validation側だけで運用記録を試す。

- manualの予想判断基準は変更しない
- 新しいスコアや馬券閾値を追加しない
- 完了率・欠測率・発走前時間への影響だけ確認

### Phase 2 — サイクル終了後の正式設計

ドライラン結果をもとにOwnerへ分解する。

候補：

- 00_core：snapshot識別、Production状態遷移、baseline参照契約
- 30_betting：購入前ゲート、実購入状態との境界
- 50_review：回顧取り込み台帳、証拠時点、KPI独立判定
- docs/validation/README.md：サイクル固有の実施状況・完了率

同じ定義を複数Ownerへ重複記載しない。

### Phase 3 — 正式変更PR

サイクル終了審査とは分離した変更PRを作る。

正式変更時は、

- 何を変更するか
- 何を変更しないか
- 既存manualとの重複
- 発走前の所要時間増
- fail-soft時の動作

を確認する。

## 15. 効果測定

本企画の目的は予想的中率を直接上げることではなく、**判断過程を正確に残し、予想改善を正しく検証できる状態にすること**である。

運用KPI候補：

| 指標 | 目標候補 |
|---|---:|
| 発走前baseline ID充足率 | 100% |
| 全体選別scope記録率 | 100% |
| 最終差分理由記録率 | 変更発生時100% |
| 単勝印整合率 | 100% |
| 購入前監査完了率 | 買い判定100% |
| 実購入状態誤計上 | 0件 |
| 回顧scope一致率 | 100% |
| KPI誤結合 | 0件 |
| 結果後証拠の事前根拠への逆流 | 0件 |
| 既存Productionの無断再生成 | 0件 |

これらは予想KPIとは別の**運用品質KPI**として測る。

## 16. 非機能要件

### 16.1 発走前時間を圧迫しない

運用精度向上のために最終予想が遅れると本末転倒。

したがって、

- snapshotヘッダは短い定型
- 差分表は変更馬だけ
- 監査結果は最終判断中心
- 未取得は推測せず明示
- ShadowよりProduction締切を優先

とする。

### 16.2 Git書き込みを発走前へ戻さない

今回の問題は「発走前にGitへ書かなかったこと」ではない。

発走前チャットsnapshotが追跡可能であれば、Git永続化は現行どおり回顧時一括を維持する。

### 16.3 将来コードをチャット予想の前提にしない

本案はチャット運用だけで成立するよう設計する。

将来的にコード化する場合でも、それは別設計とし、チャット予想で未実装コードを存在するものとして扱わない。

## 17. リスクと対策

| リスク | 対策 |
|---|---|
| 出力が長くなる | 人間向け本文とは別に短いsnapshot表を1つ置く |
| ID管理が煩雑 | race_idと日時から人間可読形式を検討 |
| チェック項目が形骸化 | 完了状態と「監査後判断」を必須にする |
| 監査に時間を使いすぎる | Production締切優先、fail-softを維持 |
| 既存manualと重複 | Ownerを先に決めてから正式実装 |
| 運用品質と予想精度を混同 | 運用KPIと予想KPIを別表で管理 |
| サイクル途中でルールが増える | 第2サイクル中はドライランのみ。正式化は別PR |

## 18. 受入テスト案

正式化前に、少なくとも次のシナリオを手順試験する。

### ケースA：全体選別16R

期待：

- 16R全てに行が存在
- 各Rにbaseline ID
- 上位5外でも区分・優先度が失われない
- prediction_scope_count=16

### ケースB：同一レースの最終予想

初期Productionがある状態で最終予想。

期待：

- 初期baselineを参照
- 変更なしならREUSED
- 変更ありなら変更馬だけ差分
- オッズだけでは能力順位を変更しない

### ケースC：既存snapshot探索失敗

期待：

- BASELINE_LOOKUP_FAILED
- 無言で新Productionへ置換しない
- 既知の発走前記録を可能な範囲で維持
- 新IDを結果後に作らない

### ケースD：▲を最も買いたい馬と評価

期待：

- 「最も買いたい」と「単勝対象」を分離
- 単勝案なら◎整合Gateで停止
- 他券種で価格を検討

### ケースE：100%馬依存

期待：

- 依存率100%自体では停止しない
- レンジ下側・軸崩れ・縦目期待値を確認
- 維持なら理由を保存

### ケースF：ユーザーが「1,500円で買う」と発言

期待：

- INTENDED
- 購入完了までは実購入帳簿へ入れない

### ケースG：Shadow未実行

期待：

- Production適格性はProduction条件だけで判定
- 該当Shadowのみ不適格
- 結果後にShadowを作らない

### ケースH：結果後コメントで新事実判明

期待：

- POST_RESULT_NEW
- 今回の事前判断理由には入れない
- 次回検証候補としてだけ保存

## 22. 推奨する進め方

最初からmanualを大きく改訂するより、

> **第2サイクル残り期間で「記録・監査のドライラン」 → サイクル終了後に運用品質だけを評価 → 必要最小限をOwner別に正式化**

の順が安全と考える。

今回の問題はルール内容そのものより実行精度にあるため、まず**「正しいルールが実際に正しく実行されたかを、後から証明できる状態」**を作ることを優先する。
