## 1. 目的

2026-09-20に発生した問題は、主として予想理論そのものではなく、

- 発走前snapshotの識別・保存内容が不十分
- 既存Productionを再利用すべき場面で再生成
- 初期→最終の差分理由が追跡できない
- 購入前監査の実施結果が記録されない
- 推奨買い目とユーザー実購入の状態を混同
- 回顧時に全体選別対象の転記が不完全
- Production / Betting / ShadowのKPI適格性を一括判定
- 結果後に判明した材料と発走前根拠の境界が曖昧

という**運用面の不正確さ・証跡不足**が確認された。ただし、未記録であることと実行されなかったことは同義ではなく、不的中の原因すべてを運用に帰するものではない。

本企画の目的は、予想ロジックを大きく変更せず、チャット実行の各段階に最低限の状態管理・完了条件・参照関係を設け、同種事故を再発しにくくすることである。

## 3. 根本原因の仮説

### 3.1 ルール不足より「実行状態」の不足

現行manualには、

- Production / Shadow分離
- baseline_forecast_id
- 同一レースProduction再利用
- 差分更新
- 単勝は原則◎
- 48.2万能軸監査
- 回顧時の全対象記録
- KPI別適格判定

など、今回必要だった原則の多くがすでに存在する。

したがって、単純にルールをさらに追加しても、実行時に「今どこまで完了しているか」を追跡できなければ再発する可能性が高い。

本企画では、**判断ルールを増やす前に、実行状態を明示し、次工程へ進む条件を固定する**ことを主な是正方向とする。

### 3.2 自由文だけでは工程境界が消える

チャットの自然文回答だけで、

- 初期Production
- 最終Production
- 価格照会
- 買い目固定
- Shadow
- 実購入
- 結果後回顧

を扱うと、同じレースの複数時点が混ざりやすい。

各回答に「これはどの状態のsnapshotか」を示す小さな構造化ヘッダが必要と考える。

### 3.3 「確認したつもり」を防ぐ完了条件が弱い

たとえば48.2は存在していても、

- 馬依存率だけ出した
- 高いと認識した
- しかしレンジ下側や軸崩れシナリオを確認していない
- 最終配分へどう反映したか残っていない

場合、監査が完了したのか判定できない。

今後は監査を**項目列挙ではなく完了条件**として扱う必要がある。

## 4. 是正方針

是正処置を6つの工程に分ける。

1. **全体選別snapshotの完全性**
2. **Production識別と差分更新**
3. **購入前監査の完了ゲート**
4. **実購入状態の明確化**
5. **回顧転記の完全性**
6. **KPI適格性の独立判定**

各工程で「最低限保存するもの」「次工程へ進める条件」「失敗時の扱い」を決める。

## 5. 是正案A — 発走前snapshotヘッダ

### 5.1 狙い

チャット回答そのものを後から一意に参照できるようにする。

### 5.2 提案する最低項目

全体選別・個別予想・最終予想では、回答の末尾または表内に次を保持する。

| 項目 | 内容 |
|---|---|
| snapshot_type | WHOLE_DAY / INITIAL_PRODUCTION / FINAL_PRODUCTION / BETTING_FIXED / SHADOW |
| race_id | 日付・場・Rを一意に識別 |
| baseline_forecast_id | 同一Production系列を追跡するID |
| manual_release | v1.6.1等 |
| fixed_at_jst | 00_coreで定義された正式固定時刻 |
| information_cutoff_jst | 使用した動的情報の締切 |
| market_used_for_ability | 必ず false / 未確認等を明示 |
| bodyweight_status | JRA取得 / fallback / 未取得 |
| production_status | NEW / REUSED / UPDATED |
| previous_snapshot_ref | 更新時だけ直前snapshotを参照 |

### 5.3 IDの扱い

IDは結果後に作らない。

`baseline_forecast_id` は新しい命名方式を作らず、既に `00_core.md` で正式定義されている、

`YYYYMMDD-競馬場-R-P連番`

をそのまま使用する。例：`20260920-NAK-09-P001`。

強い非価格情報で正式更新した場合だけ新しい連番を発行し、旧IDとの変更理由を保存する。オッズ更新だけで新IDを発行しない。snapshot自体の一意性は別の `snapshot_id` で管理する。

### 5.4 全体選別時の完全性

モード2で16Rを対象にしたなら、16R全てについて最低限、

- race_id
- ◎〜上位候補
- 勝率等のProduction確率
- 予想確信度
- 選別区分
- 購入優先度
- baseline_forecast_id

を1行以上残す。

**購入優先上位5外は見送りではない。**

上位5は「最終検討対象」であって、6位以下の買い / 見送り判定は別フィールドで管理する。

## 6. 是正案B — Production差分更新ゲート

### 6.1 狙い

同一レースを再予想するとき、既存Productionを見失ってゼロから再生成しない。

### 6.2 最終予想開始時の確認

最終予想に入る前に、必ず次の順で確認する。

1. race_id一致
2. manual_release一致
3. baseline_forecast_idの存在
4. 初期Production順位・確率・確信度
5. 初期時点の馬場等、既に織り込み済みの動的情報
6. 新たに追加された非価格情報

### 6.3 差分表

順位・確率・確信度を変更する場合、最低限次を残す。

| 対象 | Before | After | 非価格理由 | 新情報か再解釈か | 証拠強度 | 情報時刻 |
|---|---|---|---|---|---|---|

重要なのは、**「理由がある」だけではなく、その理由が初期予想後に新しく発生した情報なのか、以前からあった情報の再解釈なのかを分ける**ことである。

静的情報の再解釈だけで順位を大きく変える場合は、なぜ初期評価が変わったかを明記する。

### 6.4 既存snapshotを取得できない場合

今後、

> 既存snapshotが見つからないので再生成する

ことを自動的に許可しない。

候補対応：

- チャット文脈に明示された既存順位がある場合は、それを再利用する。
- baseline IDだけ不明なら「ID未確認」とし、新IDを勝手に発行しない。
- 順位自体が取得できない場合は BASELINE_LOOKUP_FAILED とし、再生成した案を既存Productionの正式更新として扱わない。
- 締切が迫る場合はfail-softで、取得できた既存情報を維持したまま動的情報だけ報告する。

## 7. 是正案C — 購入前4ゲート

購入案をユーザーへ出す前に、次の4ゲートを通す。

### Gate 1：券種適合

- 単勝対象は◎か
- 馬連 / ワイドの自然な本線が欠けていないか
- 券種が予想シナリオと整合しているか

中山9Rの▲単勝はここで停止できる。

### Gate 2：価格

各買い目について、

- 使用オッズ
- 取得時刻
- 的中成立に必要な確率
- 自分の推定成立確率
- 合理的レンジ
- レンジ下側
- 買い条件との余裕

を確認する。

複数馬券では、単純な各馬勝率ではなく**券種成立確率**として扱う。

### Gate 3：馬依存

最大馬依存率を算出する。

ただし70%・100%を一律禁止しない。

高依存でも、

- 依存馬が崩れる独立シナリオが小さい
- レンジ下側でも期待値が維持
- 縦目が独立して期待値負
- 集中の理由を説明可能

なら維持を許容する。

重要なのは**依存率を出した後の判断**を保存すること。

### Gate 4：監査後の最終判断

最後に必ず、

- 維持
- 配分変更
- 総投資削減
- 見送り

のいずれかを記録し、1〜2文で理由を付ける。

この最終判断がなければ、48.2監査は「実施済み」としない。

## 8. 是正案D — 実購入状態の3段階化

推奨と実購入を混同しないため、状態を分ける。

| 状態 | 意味 | 実購入帳簿 |
|---|---|---|
| RECOMMENDED | アシスタントが買い目を提示 | 算入しない |
| INTENDED | ユーザーが「これを買う」等の意思を表明したが、購入完了は未確認 | 算入しない |
| PURCHASE_CONFIRMED | ユーザーが「買いました」「購入しました」または実購入一覧を提示 | 算入する |

金額・買い目が曖昧なら推測で補わない。

これにより、阪神7Rのような「1,500円条件の買い目提案」を購入済みとして誤計上することを防ぐ。

## 9. 是正案E — 回顧開始時の取り込み台帳

回顧を始めるとき、結果を見る前後の診断より先に「発走前記録を取り込む工程」を置く。

### 9.1 回顧入力台帳

最初に次を作る。

| race_id | 初期Production | 最終Production | Betting固定 | Shadow | 実購入確認 | 結果 |
|---|---|---|---|---|---|---|

この時点で prediction_scope_count と行数を照合する。

### 9.2 完了条件

- 全体選別16Rなら16行ある
- 各行は「確認済み / 未確認」を持つ
- 未確認を「見送り」「非該当」に置換しない
- 結果から欠損した印・確率・Shadowを再構成しない
- 個別最終5Rだけ詳細がある場合でも、残り11Rの存在を消さない

### 9.3 証拠時点タグ

回顧で使う材料を、

- PRE_RACE_RECORDED
- PRE_RACE_AVAILABLE_BUT_NOT_RECORDED
- POST_RESULT_NEW

に分ける。

POST_RESULT_NEW は次回仮説の候補にはできるが、今回の事前判断理由には使わない。

## 10. 是正案F — KPI適格性マトリクス

KPIはレース単位で一括して「適格 / 不適格」としない。

### 10.1 独立判定

現行の正式Production予想精度KPIは、validation READMEで定義された必須条件一式を維持する。順位だけ、確率だけを切り出して正式適格化する変更は本企画では行わない。

そのうえで、**Production / Betting / 各Shadowを相互に巻き込んで一括除外しない**ことを徹底する。

| KPI系統 | 主な必須条件 | 他KPI欠落の影響 |
|---|---|---|
| Production予想精度 | 現行validation READMEの必須条件一式：baseline ID、レース・時刻、順位・印・確率、予想確信度、当日馬体重取得状態等 | Betting / Shadow欠落では除外しない |
| Betting ROI | Production適格＋買い/見送り判定＋使用価格・時刻＋固定10,000円案等 | Shadow欠落では除外しない |
| 51B | 発走前51B固定 | Productionが適格でも51B欠落なら51Bだけ除外 |
| E-09 | 発走前E-09固定 | 同上 |
| E-11/E-12 | Production買い目固定後の発走前比較案 | Production ROIとは別 |
| E-13 | P/A/Bの同一入力・発走前固定 | E-13欠落はProductionを落とさない |

順位捕捉、確率校正、買い目接続等は**原因診断の内訳**として分けて見るが、現行の正式適格条件を分割・緩和しない。

### 10.2 判定履歴

適格性を後から修正する場合、

- 変更前
- 変更後
- 転記漏れだった発走前証拠
- 変更日時

を残す。

結果後に新しい値を作って適格化しない。

## 11. 運用上の状態遷移

以下は初版の工程整理であり、実行順序の正本ではない。予想Shadowと買い目Shadowを一つのS6にまとめた点は不十分だった。実行時は `00_core` 0.0.0の「Production基準予想固定 → Shadow比較予想固定 → Production基準買い目固定 → Shadow比較買い目固定」を優先し、第23節の是正対象とする。

    S0 対象登録
     ↓
    S1 INITIAL_PRODUCTION_FIXED
     ↓
    S2 DYNAMIC_INFO_UPDATED
     ↓
    S3 FINAL_PRODUCTION_FIXED
     ↓
    S4 BETTING_AUDIT_COMPLETE
     ↓
    S5 BETTING_FIXED
     ↓
    S6 SHADOW_COMPLETE / SHADOW_PARTIAL
     ↓
    S7 USER_PURCHASE_STATE_RECORDED
     ↓
    S8 RESULT_REVIEW_INGESTED
     ↓
    S9 REVIEW_COMPLETED

各状態は前状態の参照を持つ。

例外：

- Shadow未完了でも、Productionは発走前に提示できる。
- ただしShadow状態を「未完了」と明示する。
- 発走後にS3以前を作り直さない。

## 12. 運用エラーコード案

自然文だけでなく、回顧で検索しやすい識別子を持つ案。

| コード案 | 意味 |
|---|---|
| BASELINE_ID_MISSING | 発走前baseline ID未固定 |
| BASELINE_LOOKUP_FAILED | 既存Productionを取得できない |
| UNJUSTIFIED_PRODUCTION_CHANGE | 差分理由・時刻・証拠が不足 |
| SINGLE_WIN_MARK_MISMATCH | 単勝対象が◎でない |
| BETTING_AUDIT_INCOMPLETE | 48.2等の購入前監査が未完了 |
| PURCHASE_STATUS_AMBIGUOUS | 購入案と購入済みを確定できない |
| REVIEW_SCOPE_MISMATCH | 事前対象数と回顧行数が不一致 |
| KPI_ELIGIBILITY_COUPLED | 独立KPIを一括除外した |
| POST_RESULT_EVIDENCE_BACKFLOW | 結果後材料を事前根拠へ混入 |
| MARKET_INDEPENDENCE_UNVERIFIED | 市場照会前の能力snapshotを確認できない |

正式なコード名称・Ownerは実施時に決める。

## 13. 直近サイクルでの適用

第2サイクルは継続中だが、本変更はProductionの能力評価・確率生成・購入閾値を変更せず、既存ルールの実行証跡を確実に残す運用是正である。

PR #34マージ後、9/21・9/22の新規対象から、**発走前snapshot永続化と強制ゲートを実運用する**。予想精度の改善効果ではなく、運用品質の完了率・欠測・時間影響を確認する。

実運用で確認するもの：

- baseline IDが発走前に残ったか
- 全体選別なら対象全Rが1行あるか
- 最終更新が差分形式になったか
- 単勝・48.2監査の完了状態が残ったか
- Shadow完了 / 未完了がProductionと分離されたか
- 実購入状態を誤計上しなかったか
- 回顧時に全対象を再取得できたか

**予想精度が良くなったかをこの2日だけで本案の採否判断に使わない。**

## 14. 実施フェーズ案

### Phase 0 — 企画確認【完了】

2026-09-20にユーザー承認。案2の発走前最小snapshot永続化を採用した。

本書の内容をレビューし、

- 実行状態を明示する方向でよいか
- チャット出力が冗長になりすぎないか
- baseline ID方式
- 購入監査の必須項目

を確定する。

### Phase 1 — サイクル中の運用是正【文書反映済み・2026-09-21以降の実運用確認待ち】

validation側の発走前snapshotと既存manualの強制ゲートを実運用する。

- manualの予想判断基準は変更しない
- 新しいスコアや馬券閾値を追加しない
- 完了率・欠測率・発走前時間への影響だけ確認

### Phase 2 — サイクル終了後の正式設計

実運用の観察結果をもとに、採用済みOwner契約の不足だけを見直す。以下の分担自体はPR #34で反映済みであり、再採用は不要。

候補：

- 00_core：snapshot識別、Production状態遷移、baseline参照契約
- 30_betting：購入前ゲート、実購入状態との境界
- 50_review：回顧取り込み台帳、証拠時点、KPI独立判定
- docs/validation/README.md：サイクル固有の実施状況・完了率

同じ定義を複数Ownerへ重複記載しない。

### Phase 3 — 正式変更PR

サイクル終了審査とは分離した変更PRを作る。

正式変更時は、

- 何を変更するか
- 何を変更しないか
- 既存manualとの重複
- 発走前の所要時間増
- fail-soft時の動作

を確認する。

## 21.1 再点検で判明した不足 — 強制力と記録耐久性

本企画の初版だけでは、今回型の不正確運用を**完全には防げない**。

理由は次の2点。

### A. ゲートが「確認推奨」に留まる危険

チェック項目が存在しても、未完了のまま最終予想・確定買い目・回顧完了へ進めるなら、今回と同じ「ルールはあったが実行されなかった」が再発する。

したがって、正式化時は各工程に **HARD STOP / FAIL-SOFT / WARNING** の3段階を持たせる。

| 不足 | 扱い |
|---|---|
| 同一レースの既存Productionを確認できない | **HARD STOP**：新しい正式Productionへ置換しない |
| 単勝対象が◎でない | **HARD STOP**：その単勝を確定買い目として出さない |
| 買い判定なのに使用価格・取得時刻がない | **HARD STOP**：確定買い目にしない |
| 48.2監査後判断がない | **HARD STOP**：BETTING_FIXEDへ進めない |
| baseline_forecast_idがない | **HARD STOP**：正式KPI適格snapshotとして固定しない |
| Shadow未完了 | **FAIL-SOFT**：Productionは維持し、Shadowだけ未完了にする |
| 当日馬体重が取得不能 | **FAIL-SOFT**：未取得を明示し確信度へ反映 |
| 補助情報不足 | **WARNING / FAIL-SOFT**：推測で埋めない |
| 回顧scope件数不一致 | **HARD STOP**：REVIEW_COMPLETEDにしない |
| 実購入完了が曖昧 | **HARD STOP**：実購入帳簿へ算入しない |

「HARD STOP」はユーザーへの回答自体を止める意味ではない。
**不足を明示したうえで、正式状態を次段階へ進めない**という意味とする。

例：

- 最終Productionを更新できない → 既存Productionを維持して最新動的情報だけ報告
- Betting監査未完了 → 「参考買い目」までは提示できるが「確定買い目」と呼ばない
- 回顧scope不一致 → 途中回顧として保存し、完了扱いにしない

### B. チャットsnapshotだけでは後日参照できない可能性

2026-09-20の再照合では、当時チャット上に存在したはずの16R全体選別のうち、現在の実行コンテキストから具体内容を復元できたのは5Rだった。

これは予想ロジックの問題ではなく、**チャットだけを永続的な監査証跡とみなすことの構造的限界**を示す。

当初は次の2案を比較した。現在は案2採用済みであり、この比較は意思決定履歴として残す。

#### 不採用案：チャット完結

発走前Git書き込みを行わず、各重要snapshotを**1つの自己完結した構造化ブロック**としてチャットへ必ず出力する。

全体選別なら16R分を1メッセージ内に完全保持し、後続の最終予想は baseline_forecast_id と previous_snapshot_ref でそのブロックを参照する。

利点：
- Git書き込みを増やさずに済む
- 予想クリティカルパスを増やしにくい

弱点：
- 実行環境が過去チャット本文を後日完全取得できない場合、監査証跡を失う可能性は残る
- この場合、回顧時に未確認として扱うしかなく、**監査可能性100%は保証できない**

#### 案2：最小限の発走前不変snapshotを永続化する

予想ロジックや分析途中経過ではなく、Production固定後の最小snapshotだけを発走前に永続化する。

候補内容：
- race_id
- baseline_forecast_id
- manual_release
- fixed_at_jst
- Production順位・確率・確信度
- 動的情報取得状態
- 買い/見送り
- 固定買い目があればその内容
- Shadow完了状態

利点：
- 回顧時の監査証跡をほぼ確実に保持
- 「あったはずだが後から読めない」を大幅に減らせる

弱点：
- 発走前に最小限とはいえGit書き込みが増える
- Git障害時には保存失敗を明示してfail-softする必要がある

**2026-09-20のユーザー判断により案2を採用する。**
分析途中のGit書き込みは行わず、正式FIXED後・チャット送信直前の最小snapshotだけを永続化する。案1は採用しない。

## 21.3 正式出力ラベルによる誤認防止

チャット上の表現も状態と連動させる。

- S1未満：**「暫定分析」**
- S3到達：**「Production最終予想」**
- S4未達：**「参考買い目」**
- S5到達：**「Production確定買い目」**

- S9到達：**「回顧完了」**

ただし、今回確認された主要な不正確運用については、

- 理由不明の差分変更

「担当」は役割案であり、人員の割当てや別モデルへの依頼を実施した意味ではない。同じモデルが自己レビューする場合も、作成した文章ではなく保存済み証跡から照合し、独立レビュー済みとは称さない。

### 23.4 保存と引継ぎの設計条件案

1. 開始時にmanualの参照コミット・release・適用日と既存snapshotの保存先を確認する。release不一致時の停止は現行契約を維持する。
2. 保存成功はリクエスト送信だけで判定せず、保存先・commit・snapshot_idを読戻して一致確認する。チャットにはその参照を付け、保存内容と矛盾する値を追加しない。
3. 同じsnapshot_id・同一内容の再送は重複追記しない。同じIDで内容が異なる場合は衝突として止める。訂正は旧記録を保持した新snapshotと参照で行う。
4. 同日ファイルの競合時は最新内容を再取得し、他チャットの追記を保持する。force更新やファイル全体の古い内容への置換をしない。権限・保護ルールを回避しない。
5. 保存の締切・再試行上限は運用開始前に決める。時刻を捏造せず、未完了なら現行の `PRE_RACE_SNAPSHOT_PERSIST_FAILED` で回答を継続する。発走後成功を発走前成功へ変更しない。
6. 固定時刻、情報締切、保存を確認した時刻は別物として扱う。Gitの時刻だけを絶対的な時刻証明とはみなさず、取得可能な送信・保存履歴を照合する。
7. 別チャット・別モデルへの引継ぎは、repo、参照commit、対象race_id、baseline、最新snapshot_id、未完了工程の短い引継ぎ票で行う。記憶や会話要約だけで再生成しない。

これらを自動検査するコードは現時点で導入しない。まずチャット運用の手順として成立するか確認し、必要なら別設計とする。
