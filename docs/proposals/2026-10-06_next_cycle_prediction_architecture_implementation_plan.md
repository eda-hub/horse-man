## 1. 目的

horse-man の責任範囲と予想生成手順を簡素化し、以下を実現する。

1. 予想そのものの精度・再現性・説明可能性を最優先にする。
2. 実購入、購入金額、実購入記録を予想システムの中核責任から外す。
3. 根拠の弱い単発情報で印や順位が揺れることを防ぐ。
4. 一方で、強い新情報が得られた場合には根拠を示して柔軟に予想を更新できるようにする。
5. 通常レースと重賞で基本予想の骨格を共通化し、重賞固有の過去傾向がProductionを過度に支配しないようにする。
6. 新しい予想材料は原則として前向きShadow検証を経てからProductionへ昇格する。
7. 将来のJRA-VAN / DuckDB実装へ接続できるデータ構造を定義する。
8. 予想後に、能力・着順適性・展開から的中しやすい推奨買い目を提示する。現行の馬券構成を流用し、オッズ取得・実購入記録を必要としない。

## 2. 今回の変更方針

次期horse-manの標準フローを次のように定義する。

```text
事実収集
  ↓
各馬の根拠評価
  ↓
勝率・連対率・3着内率・不確実性
  ↓
Production順位
  ↓
印
  ↓
券種選択・推奨買い目構成（オッズ非依存）
  ↓
予想・推奨買い目の発走前固定
  ↓
結果照合
  ↓
回顧
  ↓
ルール改善候補
```

推奨買い目の提示までを標準フローに含める。実購入・購入意思の確認・購入記録は含めない。標準最終予想では印だけで終わらず、推奨買い目または根拠付きの「推奨なし」を提示する。初回予想の構成は暫定として扱い、最終予想と区別する。

オッズは、能力順位や標準推奨買い目を変更する材料ではなく、市場との乖離分析、価格予測評価、任意の仮想収益検証に利用する。推奨買い目の生成・提示・保存は市場情報なしで成立させる。実際に何を購入するか、いくら購入するか、実際に購入したかはユーザー判断とする。

## 3. 変更しないもの

次の原則は維持する。

- AIを予想エンジン本体にしない。
- Production / Shadowを完全分離する。
- 結果を見た後に発走前Productionを遡及変更しない。
- `baseline_forecast_id` による同一予想追跡を維持する。
- 市場価格だけで能力順位・印・基準確率を変更しない。
- 見送り相当の低確信レースも、予想精度の検証対象から消さない。
- 過去snapshot・過去回顧・旧☆印を新体系へ遡及変換しない。
- バックテスト・再演では `data_cutoff` より未来の情報を使用しない。

## 5. 変更1: horse-manの責任範囲再定義

### 5.1 廃止対象

以下はhorse-manの正式責任範囲から外す。

- ユーザーの実購入意思の状態管理
- 実購入金額
- 実購入券種・組み合わせ
- 実購入収支
- 実購入ROI
- ユーザー予算に応じた最終馬券最適化
- 実購入完了確認を前提とするフロー

### 5.2 残す対象

- Production予想
- 順位
- 印
- 推奨券種・具体的な組み合わせ・点数・優先順位・構成理由
- 推奨買い目の固定履歴と結果照合（実購入とは分離）
- 勝率・連対率・3着内率
- 予想確信度
- 各評価の根拠
- 初回→最終の変更履歴
- 結果
- 予想誤差分類
- 回顧
- Shadow比較
- オッズ予測の性能評価
- 必要に応じた固定ルールによる仮想収益検証

### 5.3 仮想馬券検証

仮想馬券はPrediction Performanceと分離した**任意の市場検証sidecar**として残す。次期標準予想・回顧の必須工程にはしない。

- 実購入とは接続しない。
- ユーザーの予算・財布事情を入力としない。
- Production予想を結果後に変更して仮想券を組み替えない。
- 固定ルールを前向きに適用する場合だけ性能評価へ利用する。
- 「見送り相当のレースだから必ず仮想精算する」という必須契約は次期仕様では廃止する。
- sidecarを実行しないレースでもPrediction KPIと回顧を完全に成立させる。
- 将来sidecar自体を削除してもPrediction層・標準推奨買い目へ影響しない疎結合構造にする。
- オッズ不要の推奨買い目提示・的中照合はこのsidecarとは別契約とし、任意の市場検証を行わない場合も提供する。

### 5.4 実購入履歴と既存記録の扱い

次期仕様では、**新しい実購入履歴をhorse-manの正式台帳へ記録する機能を廃止する**。実購入の有無、券種、金額、払戻、実購入ROIをPredictionの入力・完了条件・KPIにしない。

一方、過去サイクルで既に保存された実購入・BET/SKIP・仮想精算記録は削除・変換しない。

- 旧記録は旧契約の履歴としてread-onlyで参照可能にする。
- 旧記録を次期Prediction KPIへ自動混入しない。
- 一般的なUser Noteへ利用者が購入メモを書いた場合も、システムはそれを実購入台帳として解釈・集計しない。
- 旧契約の監査・再現では、その記録当時のmanual release / gate schema / KPI contractを使用する。

この変更により、現行 `AGENTS.md` の購入／見送り履歴、見送りを含む仮想精算、Betting gate必須化と、`DECISIONS.md` のBET/SKIP・手動購入記録・Betting監査に関する決定は次期仕様と衝突する。正式切替時に13.8の方針で同時更新する。

## 6. 変更2: ☆印廃止

既存 `docs/proposals/2026-09-20_retire_star_mark_next_cycle.md` を基礎とする。

### 6.1 次期基本印体系

原則として以下を使用する。

```text
1位: ◎
2位: ○
3位: ▲
4位: △1
5位: △2
6位: △3
```

選択頭数はレース構造に応じて6頭未満を認める。

### 6.2 原則

- 人気薄だから☆を付ける処理を廃止する。
- 妙味・価格は印へ混ぜない。
- **印はProduction順位に従って付与し、印の意味に合わせるために順位を操作しない。**
- 合理的な勝利シナリオを持つ馬が4頭以上いる混戦でも、4位以下は順位どおり△1以降とする。
- 4位以下の勝利可能性は、勝率、確率レンジ、不確実性、勝利シナリオ等の独立項目で表現し、「勝てる可能性があるから▲へ昇格」という処理をしない。
- △は順位付きの下位候補であり、「勝利可能性なし」を意味しない。
- 過去の☆は変更しない。
- サイクル横断比較では印記号だけでなくProduction順位を正本として扱う。

既存の☆廃止proposalに「勝てる主要候補なら▲までに置く」等の表現が残る場合は、正式実装前に本原則へ合わせて修正する。

## 7. 変更3: 根拠を必須にする予想契約

### 7.1 基本原則

印を直接付与・除外しない。

必ず次の順序を守る。

```text
新しい事実
  ↓
影響する評価項目を特定
  ↓
評価方向と強さを決定
  ↓
確率・不確実性を更新
  ↓
Production順位を再整合
  ↓
結果として印が変わる
```

### 7.2 各評価根拠の最低項目

可能な範囲で次を構造化する。

- `factor`: 基礎能力 / 近走内容 / 相手レベル / 適性 / 展開 / 状態 / 血統 / 騎手 / 厩舎 / その他
- `fact`: 評価根拠となる確認済み事実
- `source_ref`: 出所
- `observed_at`: 情報時点
- `direction`: plus / neutral / minus / uncertain
- `strength`: strong / medium / weak
- `applies_to`: 能力 / 今回発揮能力 / 不確実性 / 展開等
- `notes`: 二重計上防止・留保

### 7.3 順位変更

初回→最終で順位を変更した場合は最低限、

- 変更前順位
- 変更後順位
- 新たに判明した事実
- 変更対象となった評価要素
- 証拠強度
- 情報時刻
- 既存評価を上回ると判断した理由

を保存する。

単一の弱いコメント、単一オッズ変動、単発の当日レース結果、単なる再考だけでは大幅な順位変更を行わない。

### 7.4 柔軟性

一貫性のために順位を固定すること自体を目的にしない。

取消、騎手変更、重大な状態変化、明確な馬場変化、複数の独立根拠が一致した新情報等が得られた場合は、根拠を示して順位・確率を変更できる。

## 8. 変更4: 近5走の相手レベル評価

現行の「相手関係を評価する」を体系化する。

### 8.1 対象

各馬の直近最大5走について評価する。

### 8.2 取得候補

- レースクラス
- 出走頭数
- 着順
- 着差
- 通過順
- 上がり
- ペース・ラップ文脈
- 勝ち馬
- 接戦馬
- 負かした馬

## 9. 変更5: 重賞Productionの通常レース化

### 9.1 方針

重賞であっても基本Productionは通常レースと同じ予想骨格で作成する。

```text
通常Production情報収集
  ↓
基本予想
  ↓
確率・順位・印FIX
  ↓
重賞固有過去傾向を取得
  ↓
比較用Shadow
```

### 9.2 重賞で追加取得してよい直接情報

馬自身に直接紐づく次の情報は、通常Productionの深掘り情報として利用してよい。

- 過去走
- 同条件実績
- 血統
- 枠×脚質
- 騎手
- 厩舎
- 当日一次情報

### 9.3 Productionへ直接使用しない重賞固有集団傾向

- 過去N年の年齢傾向
- 枠傾向
- 前走ローテ集計
- 人気構造
- レース固有血統集計
- その他レース単位の歴史的集団傾向

これらはProduction固定後に比較し、Shadowとして追加価値を検証する。

### 9.4 受入条件

- 過去傾向を見てから通常Productionを作り直さない。
- 重賞でも通常レースと同じ基本評価項目を欠落させない。
- 重賞傾向が有効だった事例だけで正式昇格しない。
- Productionと重賞傾向Shadowを同一条件で比較できる。

### 14.4 execution gate / checker / 監査互換

現行 `scripts/check_prediction_compliance.py` は `SUPPORTED_RELEASE = 'v1.6.1'`、`schema_version=prediction-compliance-v1` を前提とし、Productionに加えてBetting/Shadow KPI、Betting object、reviewの `prediction / price / betting` layerを要求する。このままmanual releaseだけを更新すると新releaseの正式保存・監査が成立しないため、正式切替の必須変更対象とする。

対象:

- `scripts/test_check_prediction_compliance.py`
- `docs/validation/execution-gates/README.md`
- 次期execution gate schema / sample、推奨買い目用の版付き契約（25.5）
- 日別record・cycle ledgerとの認証リンク
- 必要に応じて `scripts/verify_prediction_persistence.py` とそのテスト
- `scripts/check_cycle03.py` / `test_check_cycle03.py` は第3サイクル旧契約の履歴checkerとして意味を変更せず保持し、次サイクル契約へ流用しない
- `scripts/check_betting_performance.py` / `test_betting_kpi_split.py` は旧契約または任意市場sidecar用として責任範囲を明示し、次期Prediction適格性の必須checkerにしない

#### 次期gateの原則

- 次期Prediction標準契約では `production` を必須、適用対象の `shadow` を独立判定する。
- 旧価格付きBetting / actual purchaseは標準Prediction gateの必須フィールド・必須KPIにしない。推奨買い目状態/構成は標準最終予想タスクの出力・保存要件にし、Prediction適格性とRecommendation適格性は分離する（25.5）。
- 任意の市場検証sidecarを実行した場合のみ、そのsidecar固有schema / KPIを別契約で検証する。
- reviewの必須layerからBettingを外し、Prediction中心の回顧が単独で完了できるようにする。
- snapshot / receipt / pre-race timing / data cutoff / manual_ref_commit等の時点証跡は維持する。

#### 旧契約互換

**既存 `prediction-compliance-v1` の意味を新仕様に上書きしない。**

checkerは少なくとも `schema_version + manual_release` で検証契約をdispatchできる構造へ変更する。

- `v1.6.1 + prediction-compliance-v1`: 現行のBetting要件を含む旧validatorで検証する。
- 次期release + 次期gate schema: Prediction中心の新validatorで検証する。
- **現行運用のFORWARD記録**はrepoの現行manual releaseとの一致を要求する。
- **履歴監査**はgate自身の `manual_release + schema_version` で旧validatorを選択し、repoの現行manual releaseが次期版であることだけを理由に旧gateを失敗させない。
- 旧validatorの契約意味はコード・fixtureで凍結し、現在のmanual本文を新仕様として読み替えて旧記録へ適用しない。
- 旧gateを新schemaへ自動変換しない。
- 旧recordに不足していた証跡を新releaseの規則で後付けして適格化しない。
- 未知のrelease/schema組み合わせはfail closedとする。

次期schemaの具体的なversion名は実装PRで確定するが、既存 `prediction-compliance-v1` を再利用して意味だけ変更することは禁止する。

#### release切替ゲート

次期manual releaseを現行化する前に以下をすべて満たす。

1. 新旧両validatorのテストが通る。
2. v1.6.1 fixtureが旧契約のままPASSする。
3. 次期fixtureが旧価格付きBetting・実購入情報なしでPrediction正式性を検証でき、推奨買い目は独立した契約で検証できる。
4. 次期fixtureへ旧Betting項目を入れてもPrediction必須契約へ逆流しない。
5. release/schema不一致・未知version・未来情報・発走後保存を拒否する。
6. validation templateとgate schemaが同じ必須項目を要求する。
7. CI / 実行手順が新checkerを呼び出す。
8. manual、validation、checkerのいずれかだけが先行した状態でmainへ切り替わらない。

### 25.3 生成・比較・監査手順

1. 保存対象のProduction順位・印・確率・確信度・根拠・基準IDを確定する。推奨構成の都合で順位や印を動かさない。
2. 勝ち切る馬が明確か、上位2頭の同時連対が妥当か、3着内の相手を絞れるか、着順指定まで説明できるかを判定する。
3. **主力券種は原則1種類、多くても2種類程度**とする現行原則を流用し、全券種を自動提示しない。
4. 選んだ券種の自然な本線を列挙し、主シナリオと両立しない組み合わせ・同一馬の重複・過剰な候補を除く。印内全頭BOXを標準にしない。
5. 着順適性・同時好走根拠・不確実性・追加点数に対するカバー改善を比較し、本線・補助候補の優先順位と採否理由を付ける。券種を変えるだけで独立リスクとみなさない。
6. ◎-○の本線欠落、3着寄り候補の馬連混入、下位候補の万能軸化、全券の単一馬依存を監査する。100%依存なら確率レンジ下側・状態/展開根拠・軸崩れシナリオを再確認し、不足なら券種再検討または推奨なしとする。依存率を下げるだけの非◎保険券は追加しない。
7. フォーメーションを具体的な組み合わせへ展開する。着順不問券は正規化して重複除去、馬単・三連単は順序を保持する。点数はユニーク組み合わせ数と一致させる。
8. 印とともに具体的な推奨構成・点数・優先順位・短い理由を提示し、同じ内容を発走前に保存・読戻しする。

的中しやすさを「点数を無制限に増やして1枚でも当たればよい」と解釈しない。券種が違えば的中条件も違うため、単勝と複勝等を単純な数値だけで横比較しない。各馬の周辺勝率・連対率・3着内率を単純に掛けて同時好走確率とせず、展開相関・排他的な着順条件を評価する。数値化可能なら算定法・確率レンジを残し、困難なら具体的シナリオと「数値未算定」を残す。精密な確率を捏造しない。

点数上限・高不確実性判定・100%依存許容の具体的数値は、現行に未確定の部分がある。Stage 2で既存基準・検証結果に対応する版付き設定を定義し、数値が未検証なら定性的判定と最小限の自然な本線に限定する。新しい閾値の効果確認はShadowで行い、暗黙にProductionへ昇格させない。

- 数値化した成立確率は算定法とレンジ、未算定ならその状態。
- 初回→最終、取消・騎手/馬場/状態変更等によるrevisionの変更理由・旧版参照。

`RECOMMENDED` は提示したことだけを表す。`INTENDED` / `PURCHASE_CONFIRMED` へ進めず、購入券・金額・実収支へ転記しない。券ごとのstakeや合計10,000円等の旧固定資金を再導入しない。

オッズだけの更新では再生成しない。新しい非価格情報ではPredictionの正式変更手順を先に実行し、対応する推奨を新revisionで作る。取消で無効になった構成をチャット出力・保存状態で有効な推奨として残さず、旧版を失効表示し履歴として保持する。新しい基準ID/Prediction revisionに古い推奨を付け替えない。発走後の補完・再演は前向き実績と区別する。

### 25.5 次期保存・機械監査とPR69への差分

PR69準備済みの `v1.7.0 + prediction-compliance-v2` は、現時点で順位・印・確率・根拠を監査し、推奨買い目は必須構造にしていない。本追加だけで実装済みと扱わない。次の変更をPR69の準備実装とStage 2の正式切替対象に追加する。

- `chatgpt_prediction_task_v17.md` / `next_cycle_execution_v17.md`、persistence-intents、execution-gates説明/sample、contract-state、compliance / persistence / cycle checkerと各テスト。
- Recommendation用の版付きschema・認証を追加し、Predictionの既存schemaの意味を無言で変更しない。準備済みv2 snapshotの履歴読取を維持する。新しい標準出力の適用境界はmanual release・推奨契約version・有効開催日で明示し、旧snapshotへの遡及必須化をしない。
- 標準最終予想タスクでは推奨の状態を必須とする。推奨ありなら構成、推奨なし/対象外なら理由を保存する。未完了は未完了のまま報告し、Prediction保存を止めない。推奨欄が欠落したタスクを「標準出力まで完了」と認証しない。
- Predictionの正式性・Recommendationの正式性・任意market validationを独立判定する。推奨生成失敗だけで保存済みPredictionを無効化せず、Prediction PASSを推奨保存完了の代わりにしない。
- 予想作成前の事前宣言へ推奨出力のscopeとartifactを含める。同一JSONに入れる場合は推奨部分を含むbytes全体をhash検証し、別artifactの場合は宣言・receipt・Prediction参照hashを照合する。
- gate・提示内容・保存済み推奨の券種、順序、組み合わせ、点数、理由、基準ID/versionを照合する。存在確認やschema名の確認だけで認証しない。
- 市場価格・実購入・旧資金監査を求めず、出走馬存在、取消、重複、券種ごとの頭数/順序、自然な本線、根拠、data cutoff、発走前保存を確認する。
- auditは全日付の対象scopeから推奨の欠落・未登録・未保存を検出する。特定日だけの例外を作らず、Actions成功だけで完了としない。
- 日別台帳では推奨対象 = 推奨あり + 根拠付き推奨なし + 対象外 + 未完了を照合し、推奨ありの的中KPI対象は適格/不適格/保留へ分割する。未完了や外れたレースを結果後に対象から落とさない。
- 旧 `v1.6.1 + prediction-compliance-v1` の価格・資金・非◎例外監査は凍結し、オッズ不要を理由に旧validatorを緩めない。

### 25.6 結果照合・KPI・アプリ接続

推奨買い目の結果照合は、固定済みユニーク組み合わせと公式着順・同着・取消等の券種別判定で行う。実購入の申告や払戻を必要としない。未確定結果・取消での無効券は保留/無効として区別し、機械的に不的中へ混ぜない。

- Prediction精度とは別に、券種別のレース的中率（その券種で1点以上的中したレース数 / 適格かつ結果確定・有効券ありの推奨レース数）、券単位的中率（的中したユニーク券数 / 同じ対象集合の有効ユニーク券数）、対象数、推奨点数、推奨なし/未完了件数を記録する。集計に使うrevisionは発走前に固定した最終版とし、初回暫定版・旧失効版を重複算入しない。
- 「どれか1枚的中した」だけを全体品質とせず、点数・券種・成立シナリオと併せて比較する。
- 順位評価ミス、券種/着順指定ミス、相手切り・点数増加、展開依存を分けて回顧する。実購入ROIは算出しない。
- 任意市場sidecarの仮想ROIは別対象集合・別KPIにし、推奨的中KPIへ混入しない。

Stage 2ではチャット出力・保存・監査の契約を先に揃える。アプリ実行コードはPhase 3で固定Prediction→推奨構成・チャット用出力・履歴/失効、Phase 6で結果照合（Phase 4の画面実装はN/A）、Phase 8で前向き評価を実装する。オッズ取得のPhase 5は推奨生成の前提にしない。既存Phase順・独立PR契約は維持し、存在しないアプリruntimeを準備実装済みと報告しない。

### 25.7 受入ケース

次のケースを準備実装・正式切替・アプリPhaseの対応表へ登録し、実施済み/未実施を明示する。

1. オッズAPIなし・市場sidecarなし・実購入情報なしで、標準最終予想→具体的な推奨→保存/読戻し→結果照合が完結する。
2. Productionと非価格根拠が同じなら、オッズ/人気だけを変えても順位・印・推奨構成・優先順位が変わらない。
3. 馬連/ワイド選択時に◎-○を自然な本線として扱い、3着寄り△を馬連へ含めず、旧☆の価格目的追加や非◎縦目例外を自動移植しない。
4. 勝ち切りが明確、上位2頭が有力、着順が不明な混戦、3着相手が複数、高不確実性、100%軸依存の各ケースで券種理由・点数・依存監査を確認する。
5. 三連複の順序違い/列重複を1点へ統合し、馬単/三連単の逆順は別券として数える。取消馬、同一馬の重複、存在しない馬、点数不一致を拒否する。
6. 推奨なしは根拠付きで保存し、生成失敗は未完了に分類する。空欄・無理由・未完了を推奨済み/保存完了として認証しない。明示的な印のみ依頼も識別する。
7. 推奨対象の△を含む各馬に着順適性・観測時刻・出所があり、未来情報・Shadow由来の構成・未算定確率の捏造を拒否する。
8. 推奨snapshotの組み合わせ・点数・理由・Prediction参照hashを改変すると認証が失敗し、未宣言/未保存/ゲート未登録もauditで検出する。
9. 取消・非価格情報更新では旧推奨を失効させ、新revisionと対応Predictionを照合する。結果後の買い目組替え・別基準IDへの付替えを前向きKPIへ認証しない。
10. 新契約に対応する日別台帳・scope・推奨認証・的中KPIを照合し、不適格/保留/未完了を削除せず、Predictionと市場sidecarから分離する。
11. 旧v1.6.1のBetting必須欠落は従来どおりFAIL、旧☆/資金/実購入記録は旧契約で読める。準備済みv2 Predictionも記録当時の契約で検証できる。
12. チャットで印＋構成＋点数＋短い理由を提示し、具体的買い目と保存/読戻し内容が完全一致する。WebUI表示の受入は対象外/N/A。予算入力・購入完了操作・新規実購入台帳を要求しない。



### 25.8 二頭軸三連系の条件付き構築・検証仮説（2026-10-10 利用者所感）

利用者所感：**「推定3着以内率70%以上が2頭いるなら三連系も検討し、三連単2頭軸マルチの相手は推定3着以内率30%以上、三連複2頭軸流しの相手は印を付けた馬の全頭を検討する。馬連・ワイド偏重ではなく、突出した優位性があれば高配当も狙いたい」**。

これは**次期推奨候補生成の検証要件**として登録する。現在のv1.6.1の買い目規約や既に発走前固定した2026-10-10予想・買い目を変更しない。上記70%・30%は利用者指定の試験用トリガーであって、統計的に校正された推奨閾値・購入必須条件ではない。

1. **起動候補**：発走前Productionで3着内率70%以上の異なる出走馬が2頭以上いる場合、候補2軸を確認する。該当馬が3頭以上の場合は2頭の選定・シナリオ根拠を明記し、全2頭組を機械的に購入案へ採用しない。該当なし・予測3着内率未算定なら起動しない（未算定を0%へ置換しない）。
2. **三連単2頭軸マルチ**：2軸A,Bの双方が1〜3着に入り、第三の馬Cが他の1〜3着に入る6通り（A/B/Cの全着順順列）を1相手につき6点生成する。相手は当該軸以外の推定3着内率30%以上の馬をまず候補にする。相手n頭なら最大6n点（同着・取消等は券種別の公式規則で別処理）。順列ごとの着順確率と第三候補の重複・同一展開依存を検討し、根拠なしに6点を当然採用しない。
3. **三連複2頭軸流し**：A,Bを軸とし、相手は**最終印を付けた全馬のうち軸を除く馬**を試験用候補とする。相手m頭ならm点、無印と取消馬は含めない。ただし、印全頭で点数・軸依存が過大となる場合は「候補全点」と「実際に推奨する点」を分離し、絞る/推奨なしも許す。出走全頭流し・印なし補完をしない。
4. **優位性の根拠**：3着内率の高さだけでは、2頭の**同時**3着内確率を証明できない。3着の排他性、脚質・馬場・隊列の相関、軸2頭が同時に凡走するシナリオ、連対/着順ごとの分布、相手馬の役割を独立評価する。各軸が単独70%でも同時率49%と安易に掛けない。数値が校正不能なら「成立確率未算定」と残し、買い必須にしない。
5. **券種選択の優先**：先に券種を馬連・ワイドへ固定せず、想定される上位2頭の好走安定性、3着相手の予測範囲、着順逆転可能性、点数・失敗条件から単勝/二連系/三連系を比較する。上位2軸の優位が飛び抜けており、三連系のカバー増分が説明できる場合は三連系を主力にしてよい。**高配当になりそう**という事実だけで勝率や推奨順位を上書きしない。市場価格・回収期待は任意market sidecarにのみ記録する。三連単と三連複を毎回合わせ買いすることも要求しない。
6. **出力と監査**：起動有無・トリガーと根拠・軸馬と各単独3着内率・2頭同時率の算定可否・相手閾値判定・候補全点/推奨採用点の差分・順列展開・採否理由・大きな失敗シナリオを保存する。三連単6nと三連複mの点数/重複を自動テストする。最低確信度や点数上限など追加数値は発走前検証母集団で評価し、Stage 2で版付き定義する。
7. **前向き検証**：結果を知る前に固定した推奨と、券種・点数をそろえた二連系対照を比較する。的中率、1レース当たり点数、カバー率、2頭軸崩壊率、三連単の着順不一致、三連複の第三馬漏れを評価する。オッズ不要の正式Recommendationは的中率・点数まで、**仮想ROIは事前に確定した買い目・額・市場時点を持つ任意sidecarだけ**で比較する。結果後に成功例だけ三連系へ組替えない。

**発見の出所を明示した回顧例（前向き成果には算入しない）**：2026-10-10東京8Rは発走前の固定Productionで⑥75%、④71%が軸条件に適合し、相手①35%、⑩32%で三連単候補12点、印内他5頭で三連複候補5点となる。当日の確定結果は④→⑥→①、払戻は三連単④-⑥-①が100円当たり2,800円、三連複①-④-⑥が730円。**結果後の構成検算**として各100円均等なら1,700円→3,530円（207.6%）。この17点は当日の発走前固定研究用5点に存在せず、2026-10-10の正式/研究用ROIに算入しない。事後例1件で将来の回収率改善や70%/30%閾値の妥当性は証明できない。出典：[JRA東京8R結果](https://app.jra.jp/JRADB/accessS.html?CNAME=sw01sde0105202604030820261010%2F88)、[払戻明細](https://race.netkeiba.com/race/result.html?race_id=202605040308)。

実装時は正常・不正・欠測・取消・履歴互換fixtureを用意し、compliance / persistence / cycleの単体テストと、標準テンプレートを使った発走前保存から結果照合までのend-to-end確認を行う。
