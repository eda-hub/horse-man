## 1. 目的と背景

予想開始時にGitHub ownerの入力不足を理由として処理を止めず、GitHub上のhorse-manを特定し、現行Productionルールに基づいて予想を進められるようにする。将来実装や未確定仕様の混入を防ぎ、利用者への問題報告は実際に発生した具体的な問題に限定する。

今回提示された是正方針を要件とする。発生時の全ログは未確認のため、根本原因が既存文書の欠落・曖昧さ・実行時の不遵守のどれにあるかは断定しない。実装開始時に既存記述を調査し、既に規定があれば重複追加より入口・適用範囲・検証の改善を優先する。

追加要望として、予想記録をmainへ直接コミットする現行運用を終了する。その日の初回予想で日次作業ブランチを一度だけ作成し、以降の予想・結果記録・回顧が完了するまで同じブランチを使用する。日付基準や例外処理は本書で実装案として具体化する。

## 2. 作成時点の確認状況

先行調査ではGitHubのリポジトリ検索と接続済みリポジトリ検索が、いずれも `HTTP 400: Invalid MCP request metadata` で失敗した。当初はこのためGitHub上の最新内容・対象ブランチ・コミットを確認できなかった。

保管時の再確認では、GitHub連携から `eda-hub/horse-man` の取得に成功し、mainの `AGENTS.md` と `docs/manual/README.md` を確認した。現行リリースは `v1.6.1`、計画書の既存配置先は `docs/proposals/` である。正本READMEではmainからのルール参照、改訂の作業ブランチ運用、発走前snapshot保存、判断の意味を変えない記録運用整理ではリリース維持が可能であることを確認した。以前の接続エラーの根本原因は未特定であり、owner誤りや権限不足とは断定しない。

本書はユーザーが決定した6項目と追加のブランチ運用要望を実装可能な手順へ具体化した計画である。入口の現行規定は確認済みだが、全関連ファイルの実装差分までは突合していない。過去のローカルコピーや会話の記憶を現行ルールの根拠にはしない。具体的な追記位置、既存プロンプトのパス、文書改訂に伴う版管理方法は、実装開始時に最新の正本と変更管理規定から確定する。

## 4. 対象範囲

対象は予想開始時の運用契約、そこへの導線、関連文書の整合、受入検証である。予想の評価方法、確率計算、買い目の判断基準、ProductionとShadowの境界は維持する。既存の保存契約のうち保存先ブランチを変更し、保存タイミング、保存パス、不変snapshot、追記方式は維持する。将来の予想システムや新しい検索サービスの開発は含めない。

問題報告の簡素化は、現行ルールが要求する予想根拠、データ不足、購入前監査、保存失敗等の報告を省略する根拠にしない。

## 6. 実装する処理手順

### 6.1 リポジトリの特定

1. 利用可能なGitHub接続でhorse-manを検索する。ownerの事前提示は要求しない。
2. 検索結果の完全名、URL、説明、manualの存在と内容から対象を特定する。名前だけで無関係な同名リポジトリを選ばない。
3. 既知のURLや完全名がある場合は候補として直接取得できる。ただし、過去の記憶だけで現在の内容やアクセス可否を確定しない。
4. 検索結果がない場合は、利用可能な接続済みリポジトリ一覧や別の検索経路で確認する。検索インデックスの欠落だけでリポジトリ不存在と判断しない。
5. 候補が複数ある場合は内容と依頼文脈で絞り込む。それでも特定できない場合に限り、候補を示して確認する。

ここでのGitHub ownerはアカウント・組織名を指す。manual内の責務を表すOwnerモジュールとは別概念として記述する。

### 6.2 正本と参照時点の確定

1. 正式ルールの参照元と記録の保存先を区別する。正式ルールはmain（別の正式運用ブランチが明示されていればそれ）から確認し、日次作業ブランチにある未承認のルール変更は使わない。
2. 正式ルール参照元のdocs/manual/README.mdを取得する。既存予想を継続・回顧する場合は、その予想に記録されたルール版・参照コミットも確認する。
3. 現行リリース、タスク別の参照先、適用条件を読む。版番号を開始プロンプトへ固定値として複製しない。
4. 可能な取得経路ではコミットSHAを確定し、後続ファイルも同じコミットから読む。SHA固定ができない場合は取得中の更新による混在を確認し、不整合があれば関連ファイルを取り直す。
5. 参照元の完全名、ブランチまたはコミット、現行リリース、取得ファイルを検証可能な形で控える。新たな分析途中のGit保存義務は設けず、現行の記録契約に従う。

### 6.3 必要なProductionルールの解決

1. 依頼が事前予想、当日補正、最終予想、買い目等のどの工程かを判定する。
2. READMEで指定される必須モジュールと、その必須依存先を取得する。
3. 読み込んだ文書のリリース整合性と適用条件を、現行の正本の規定に従って確認する。
4. リンク先をすべて正式ルールと見なさない。Production、Shadow、検証記録、参考資料、将来設計の位置付けを確認する。
5. 必要なルールが揃えば予想を進める。将来のローカル実装や未接続の取得機能を、稼働済みの前提にしない。

### 6.4 問題発生時の分岐

| 状況 | 対応 | 報告・確認の条件 |
| --- | --- | --- |
| owner未記載 | GitHub検索で補完する | 未記載だけでは報告・確認しない |
| 検索失敗、直接取得は成功 | 取得結果で対象とルールを確認し継続する | 判断・実行に支障が残らなければ追加確認不要 |
| 候補が複数で特定不能 | 候補と識別点を示す | 対象選択に必要な確認だけを求める |
| 認証・権限・接続エラー | 利用可能な別経路を試し、同じ失敗を無制限に反復しない | 解消しない事象と実施済みの対応を報告する |
| READMEまたは必須ルール欠落 | 対象パスと参照関係を確認する | 影響する予想判断を保留し、欠落対象を報告する |
| 必須ルールの版不整合・矛盾 | 同じ参照時点で取り直し、解消するか確認する | 残る不整合箇所と影響を報告し、独自解釈で補完しない |
| 非必須の参考資料だけ取得不能 | 現行ルールで許される範囲で継続する | 品質・出力への実際の影響があればその範囲を明記する |

問題報告の形式は「対象／発生事象／試した対応／予想への影響／必要な対応」を基本とする。利用可能な復旧手段を実施する前に、ownerの再提示や利用者の承認を一律に要求しない。

### 6.5 日次作業ブランチの作成・再利用

以下の名称・管理方式は追加要望に対する実装案とする。既存の命名規約がある場合は、日付から一意に探索できる性質を保って合わせる。

| 項目 | 方針 |
| --- | --- |
| 作業日 | 初回予想を開始する日の日本時間（Asia/Tokyo）。UTCの日付やレース開催日と混同しない |
| ブランチ名案 | `prediction/YYYY-MM-DD`（例：`prediction/2026-09-22`） |
| 作成単位 | 1作業日につき1本。レース・チャット・予想更新ごとには作らない |
| 作成時点 | 対象と正式ルールを確認した後、その日の初回予想で、記録の初回保存より前に作成 |
| 作成元 | 作成時点のGitHub上のmain先端コミット。別日の未完了ブランチから派生させない |
| 保存対象 | その日の新規予想と、それらに関連する当日更新、買い目、結果、回顧、必要な長期記録への反映 |
| 使用期限 | 所属する予想の更新と回顧が全て完了するまで。日付変更だけでは終了しない |
| main反映 | 全対象の回顧・整合確認後にPRで反映する案。今回の追加要望を自動マージ・自動削除の許可とは扱わない |

開始時はまず、依頼が既存予想の継続・回顧なのか、新しい予想なのかを判定する。既存予想の場合は予想ID・レース・作業記録から元のブランチを取得する。新規予想の場合に本日のブランチを検索し、存在すれば再利用し、存在しない場合だけ作成する。検索エラーを「存在しない」とみなして作成しない。

同日の複数レースは1本へ集約する。前日の予想の回顧と、本日の新規予想を同時に行う場合は、それぞれ元の日次ブランチと本日の日次ブランチを使用する。前日からの予想を当日の新規予想として作り直さない。レース開催日が未来でも、所属日は初回予想を開始した作業日とする。

同名ブランチが既に存在する場合は、日次作業の内容を確認して再利用する。同時開始によって作成が競合した場合も、作成済みのブランチを再取得する。別名の枝を増やしたり既存ブランチをmainへリセットしたりしない。同名だが用途が異なる場合だけ具体的な衝突を報告する。

### 6.6 保存・再開・競合時の契約

1. 予想と回顧の書込時は日次ブランチを必ず明示する。main・デフォルトブランチへの暗黙の保存や、作業ブランチへの保存失敗時のmainへの切替を禁止する。
2. チャット再開時は日次ブランチ上の最新記録を読む。mainだけを読んで未マージの予想が存在しないと判断しない。参照ブランチを指定できるファイル取得を使い、デフォルトブランチだけを検索する機能に依存しない。
3. 既存の予想IDと正式snapshotを維持する。ブランチ変更やチャット変更を理由にProductionを再生成しない。既存予想のルール版は記録された根拠から確認し、正式な更新条件なしに最新版へ置き換えない。新規予想は開始時の正式ルールを確認するため、日次ブランチを作成した時点のmanualを無条件に一日中使用する方式にはしない。
4. 発走前に必要な正式snapshotは、現行契約の時点・パス・追記方式を維持してGitHub上の日次ブランチに永続化する。ローカルコミットだけで完了とせず、リモートの保存成功とコミットを確認する。mainへのPRマージは永続化の条件にしない。
5. 更新直前に対象ブランチの先端と対象ファイルの状態を確認する。並行更新を検出した場合は最新内容を取得して追記差分を再構成する。同じ予想の二重追記を照合し、force pushや他の記録を消す全文上書きをしない。意味上の競合が残る書込だけを保留して報告する。
6. ブランチ作成・保存の失敗は対象名、事象、影響を報告する。保存していない予想を保存済みと表現しない。発走前に保存できなかった記録を後から発走前証跡として扱わない。

作業を別チャットから復元できるよう、作業日、ブランチ名、mainの基点コミット、予想IDとレースの対応、各予想のルール参照コミット・版、回顧の進捗を保持する。既存記録で充足すれば新しい台帳を増やさない。不足する場合の配置案は `docs/validation/work_sessions/YYYY-MM-DD.md` とし、実装時に既存の保存責務・保持期間と突合する。初回の正式記録保存に合わせて必要な情報を記録し、分析途中の思考ログの保存は追加しない。

ブランチが存在するが正式記録がまだない状態は、初回予想の中断として再開できるようにする。履歴があるはずのブランチが見つからない場合は、PR・コミット・既存記録から所在を確認し、空のブランチを作って完了済みと扱わない。

### 6.7 完了・main反映・導入時の移行

日次作業の完了は、所属する全予想について必要な結果と回顧が記録され、未処理の対象がないことで判定する。見送りレースも既存ルールに従って含め、中止・結果待ち等は状態を明記する。1レースの回顧終了で日次全体を完了扱いにしない。

mainへの反映方式は、同じ日次ブランチからmain向けPRを用意し、差分のセルフレビューと必要な検証後に既存の承認・マージ規定へ従う案とする。回顧完了とマージ済みは別の状態として記録する。未マージの間は枝を保持し、途中で追加の依頼があれば再利用する。

同日に完了後さらに予想が追加された場合も同じブランチを再開する。既にPRがマージ済みならその事実とmainへの反映状況を確認してから再利用し、PRが閉じていれば追加分用のPRで扱う。取り込み済みの記録を再変更・重複反映しない。必要に応じてmainを通常のマージで取り込み、force pushや履歴のリセットは行わない。ブランチの自動削除は導入しない。

別の日次ブランチとmainで同じファイルが更新されていた場合は、双方の記録を保ったうえで競合を解消する。特に長期傾向ファイルのように追記だけでない変更は、差分の意味を確認してセルフレビューする。未マージの別日データが必要な場合はそのブランチを明示して参照し、別日のブランチ全体を無条件に取り込まない。

導入時にmain上で進行中の予想がある場合は、次の継続作業時にその記録を含むmainから導入日の日次ブランチを一度作成し、既存の予想IDを引き継ぐ。これは初回予想時作成の原則に対する移行時だけの例外とする。mainの過去コミットを削除・書換えず、以降の更新と回顧だけを作業ブランチへ保存する。

## 9. セルフレビュー観点

- owner未記載と、検索後も対象を特定できない状態を区別できているか。
- 取得前の入口が機能し、READMEが現行ルールの正である関係を維持しているか。
- READMEから必要なProductionルールへ到達でき、将来仕様とShadowが混入しないか。
- 「問題がある場合だけ報告」が、必須の監査・欠落・保存失敗の隠蔽に使われないか。
- 新しい承認待ち、必須入力、分析途中の保存義務を不要に増やしていないか。
- 評価式、買い目、ルール昇格、既存記録、ProductionとShadowの境界を変更していないか。
- 予想・回顧の全書込先が日次ブランチとなり、再開時の読込も同じブランチになっているか。
- 翌日の回顧、並行チャット、途中移行でブランチの重複や記録の上書きが起きないか。
- 発走前の永続化がPRマージ待ちになっていないか。

## 10. 完了条件と切り戻し

以下を満たした時点で是正実装の完了とする。

1. R1～R9が実装され、入口・正本・関連手順の整合が取れている。
2. 必須の受入検証が合格し、実行証跡と模擬検証の区別が記録されている。
3. 変更の本質部分をセルフレビューし、未解決の重大な矛盾がない。
4. 文書改訂が現行の変更管理規定を満たしている。
5. 実際の予想判断基準を変更していないことを差分で確認している。
6. 初回だけの日次ブランチ作成、別チャットでの再利用、翌日の回顧、発走前のリモート保存を確認し、予想・回顧のmain直接コミット経路が残っていない。

不具合が発生した場合は、本是正で変更した文書・開始指示の差分だけを切り戻す。後続の変更や既存の予想・回顧記録を巻き戻さない。切り戻し後もユーザーが決定した6項目とmain直接コミット禁止は是正要件として保持し、問題箇所を修正して再検証する。

日次ブランチ運用の不具合時もmain直接コミットへ戻さない。安全に保存できない書込だけを保留し、既存の作業ブランチ・予想履歴を保全して修復する。
