## 1. 目的と背景

予想開始時にGitHub ownerの入力不足を理由として処理を止めず、GitHub上のhorse-manを特定し、現行Productionルールに基づいて予想を進められるようにする。将来実装や未確定仕様の混入を防ぎ、利用者への問題報告は実際に発生した具体的な問題に限定する。

今回提示された是正方針を要件とする。発生時の全ログは未確認のため、根本原因が既存文書の欠落・曖昧さ・実行時の不遵守のどれにあるかは断定しない。実装開始時に既存記述を調査し、既に規定があれば重複追加より入口・適用範囲・検証の改善を優先する。

追加要望として、予想記録をmainへ直接コミットする現行運用を終了する。その日の初回予想で日次作業ブランチを一度だけ作成し、以降の予想・結果記録・回顧が完了するまで同じブランチを使用する。日付基準や例外処理は本書で実装案として具体化する。

さらに、ユーザーから「GPTのタスク開始時刻を発走時刻と取り違え、snapshotを保存しなかった」との事象報告を受けた。報告された事象を再現ケースに固定し、時刻の出所確認、保存判断、保存後照合の各段階で誤認を検出する。事故時のチャット全ログは未確認であり、内部原因の確定と再発防止策の設計を区別する。第4版では対象日snapshot内の10R・12Rの運用事象を具体的な是正根拠に追加した。

## 2. 作成時点の確認状況

先行調査ではGitHubのリポジトリ検索と接続済みリポジトリ検索が、いずれも `HTTP 400: Invalid MCP request metadata` で失敗した。当初はこのためGitHub上の最新内容・対象ブランチ・コミットを確認できなかった。

保管時の再確認では、GitHub連携から `eda-hub/horse-man` の取得に成功し、mainの `AGENTS.md` と `docs/manual/README.md` を確認した。現行リリースは `v1.6.1`、計画書の既存配置先は `docs/proposals/` である。正本READMEではmainからのルール参照、改訂の作業ブランチ運用、発走前snapshot保存、判断の意味を変えない記録運用整理ではリリース維持が可能であることを確認した。以前の接続エラーの根本原因は未特定であり、owner誤りや権限不足とは断定しない。

本書はユーザーが決定した6項目と追加のブランチ運用要望を実装可能な手順へ具体化した計画である。入口の現行規定に加え、第3版では00_coreのsnapshot契約・情報時点判定とsnapshot READMEを確認した。両者にはmain限定の保存成功条件があるため、日次ブランチ化の実装では同時改訂が必須となる。全関連ファイルの実装差分までは突合していない。過去のローカルコピーや会話の記憶を現行ルールの根拠にはしない。具体的な追記位置、既存プロンプトのパス、文書改訂に伴う版管理方法は、実装開始時に最新の正本と変更管理規定から確定する。

## 6. 実装する処理手順

### 6.1 リポジトリの特定

1. 利用可能なGitHub接続へ `eda-hub/horse-man` を直接指定する。プロジェクト指示で対象が確定しているため、ownerの再提示や汎用検索を開始条件にしない。
2. 指定先のmanualの存在・内容・アクセス可否を確認する。無関係な同名リポジトリへ切り替えない。
3. 指定URLは `https://github.com/eda-hub/horse-man.git` とする。過去の記憶だけで現在の内容やアクセス可否を確定しない。
4. 検索結果がない場合は、利用可能な接続済みリポジトリ一覧や別の検索経路で確認する。検索インデックスの欠落だけでリポジトリ不存在と判断しない。
5. 同名候補が複数あっても指定済みのeda-hub/horse-manを使用する。利用者から対象変更の指示がない限り、候補選択を再要求しない。

ここでのGitHub ownerはアカウント・組織名を指す。manual内の責務を表すOwnerモジュールとは別概念として記述する。

### 6.2 正本と参照時点の確定

1. 正式ルールの参照元と記録の保存先を区別する。正式ルールはmain（別の正式運用ブランチが明示されていればそれ）から確認し、日次作業ブランチにある未承認のルール変更は使わない。
2. 正式ルール参照元のdocs/manual/README.mdを取得する。既存予想を継続・回顧する場合は、その予想に記録されたルール版・参照コミットも確認する。
3. 現行リリース、タスク別の参照先、適用条件を読む。版番号を開始プロンプトへ固定値として複製しない。
4. 可能な取得経路ではコミットSHAを確定し、後続ファイルも同じコミットから読む。SHA固定ができない場合は取得中の更新による混在を確認し、不整合があれば関連ファイルを取り直す。
5. 参照元の完全名、ブランチまたはコミット、現行リリース、取得ファイルを検証可能な形で控える。新たな分析途中のGit保存義務は設けず、現行の記録契約に従う。

### 6.3 必要なProductionルールの解決

1. 依頼が事前予想、当日補正、最終予想、買い目等のどの工程かを判定する。
2. READMEで指定される必須モジュールと、その必須依存先を取得する。
3. 読み込んだ文書のリリース整合性と適用条件を、現行の正本の規定に従って確認する。
4. リンク先をすべて正式ルールと見なさない。Production、Shadow、検証記録、参考資料、将来設計の位置付けを確認する。
5. 必要なルールが揃えば予想を進める。将来のローカル実装や未接続の取得機能を、稼働済みの前提にしない。

### 6.4 問題発生時の分岐

| 状況 | 対応 | 報告・確認の条件 |
| --- | --- | --- |
| owner未記載 | 設定済みのeda-hub/horse-manを直接取得する | 未記載だけでは報告・確認しない |
| 検索失敗、直接取得は成功 | 取得結果で対象とルールを確認し継続する | 判断・実行に支障が残らなければ追加確認不要 |
| 候補が複数で特定不能 | 候補と識別点を示す | 対象選択に必要な確認だけを求める |
| 認証・権限・接続エラー | 利用可能な別経路を試し、同じ失敗を無制限に反復しない | 解消しない事象と実施済みの対応を報告する |
| READMEまたは必須ルール欠落 | 対象パスと参照関係を確認する | 影響する予想判断を保留し、欠落対象を報告する |
| 必須ルールの版不整合・矛盾 | 同じ参照時点で取り直し、解消するか確認する | 残る不整合箇所と影響を報告し、独自解釈で補完しない |
| 非必須の参考資料だけ取得不能 | 現行ルールで許される範囲で継続する | 品質・出力への実際の影響があればその範囲を明記する |

問題報告の形式は「対象／発生事象／試した対応／予想への影響／必要な対応」を基本とする。利用可能な復旧手段を実施する前に、ownerの再提示や利用者の承認を一律に要求しない。

### 6.5 日次作業ブランチの作成・再利用

以下の名称・管理方式は追加要望に対する実装案とする。既存の命名規約がある場合は、日付から一意に探索できる性質を保って合わせる。

| 項目 | 方針 |
| --- | --- |
| 作業日 | 初回予想を開始する日の日本時間（Asia/Tokyo）。UTCの日付やレース開催日と混同しない |
| ブランチ名案 | `prediction/YYYY-MM-DD`（例：`prediction/2026-09-22`） |
| 作成単位 | 1作業日につき1本。レース・チャット・予想更新ごとには作らない |
| 作成時点 | 対象と正式ルールを確認した後、その日の初回予想で、記録の初回保存より前に作成 |
| 作成元 | 作成時点のGitHub上のmain先端コミット。別日の未完了ブランチから派生させない |
| 保存対象 | その日の新規予想と、それらに関連する当日更新、買い目、結果、回顧、必要な長期記録への反映 |
| 使用期限 | 所属する予想の更新と回顧が全て完了するまで。日付変更だけでは終了しない |
| main反映 | 全対象の回顧・整合確認後にPRで反映する案。今回の追加要望を自動マージ・自動削除の許可とは扱わない |

開始時はまず、依頼が既存予想の継続・回顧なのか、新しい予想なのかを判定する。既存予想の場合は予想ID・レース・作業記録から元のブランチを取得する。新規予想の場合に本日のブランチを検索し、存在すれば再利用し、存在しない場合だけ作成する。検索エラーを「存在しない」とみなして作成しない。

同日の複数レースは1本へ集約する。前日の予想の回顧と、本日の新規予想を同時に行う場合は、それぞれ元の日次ブランチと本日の日次ブランチを使用する。前日からの予想を当日の新規予想として作り直さない。レース開催日が未来でも、所属日は初回予想を開始した作業日とする。

同名ブランチが既に存在する場合は、日次作業の内容を確認して再利用する。同時開始によって作成が競合した場合も、作成済みのブランチを再取得する。別名の枝を増やしたり既存ブランチをmainへリセットしたりしない。同名だが用途が異なる場合だけ具体的な衝突を報告する。

### 6.6 保存・再開・競合時の契約

1. 予想と回顧の書込時は日次ブランチを必ず明示する。main・デフォルトブランチへの暗黙の保存や、作業ブランチへの保存失敗時のmainへの切替を禁止する。
2. チャット再開時は日次ブランチ上の最新記録を読む。mainだけを読んで未マージの予想が存在しないと判断しない。参照ブランチを指定できるファイル取得を使い、デフォルトブランチだけを検索する機能に依存しない。
3. 既存の予想IDと正式snapshotを維持する。ブランチ変更やチャット変更を理由にProductionを再生成しない。既存予想のルール版は記録された根拠から確認し、正式な更新条件なしに最新版へ置き換えない。新規予想は開始時の正式ルールを確認するため、日次ブランチを作成した時点のmanualを無条件に一日中使用する方式にはしない。
4. 発走前に必要な正式snapshotは、現行契約の時点・パス・追記方式を維持してGitHub上の日次ブランチに永続化する。ローカルコミットだけで完了とせず、リモートの保存成功とコミットを確認する。mainへのPRマージは永続化の条件にしない。
5. 更新直前に対象ブランチの先端と対象ファイルの状態を確認する。並行更新を検出した場合は最新内容を取得して追記差分を再構成する。同じ予想の二重追記を照合し、force pushや他の記録を消す全文上書きをしない。意味上の競合が残る書込だけを保留して報告する。
6. ブランチ作成・保存の失敗は対象名、事象、影響を報告する。保存していない予想を保存済みと表現しない。発走前に保存できなかった記録を後から発走前証跡として扱わない。

作業を別チャットから復元できるよう、作業日、ブランチ名、mainの基点コミット、予想IDとレースの対応、各予想のルール参照コミット・版、回顧の進捗を保持する。既存記録で充足すれば新しい台帳を増やさない。不足する場合の配置案は `docs/validation/work_sessions/YYYY-MM-DD.md` とし、実装時に既存の保存責務・保持期間と突合する。初回の正式記録保存に合わせて必要な情報を記録し、分析途中の思考ログの保存は追加しない。

ブランチが存在するが正式記録がまだない状態は、初回予想の中断として再開できるようにする。履歴があるはずのブランチが見つからない場合は、PR・コミット・既存記録から所在を確認し、空のブランチを作って完了済みと扱わない。

### 6.7 完了・main反映・導入時の移行

日次作業の完了は、所属する全予想について必要な結果と回顧が記録され、未処理の対象がないことで判定する。見送りレースも既存ルールに従って含め、中止・結果待ち等は状態を明記する。1レースの回顧終了で日次全体を完了扱いにしない。

mainへの反映方式は、同じ日次ブランチからmain向けPRを用意し、差分のセルフレビューと必要な検証後に既存の承認・マージ規定へ従う案とする。回顧完了とマージ済みは別の状態として記録する。未マージの間は枝を保持し、途中で追加の依頼があれば再利用する。

同日に完了後さらに予想が追加された場合も同じブランチを再開する。既にPRがマージ済みならその事実とmainへの反映状況を確認してから再利用し、PRが閉じていれば追加分用のPRで扱う。取り込み済みの記録を再変更・重複反映しない。必要に応じてmainを通常のマージで取り込み、force pushや履歴のリセットは行わない。ブランチの自動削除は導入しない。

別の日次ブランチとmainで同じファイルが更新されていた場合は、双方の記録を保ったうえで競合を解消する。特に長期傾向ファイルのように追記だけでない変更は、差分の意味を確認してセルフレビューする。未マージの別日データが必要な場合はそのブランチを明示して参照し、別日のブランチ全体を無条件に取り込まない。

導入時にmain上で進行中の予想がある場合は、次の継続作業時にその記録を含むmainから導入日の日次ブランチを一度作成し、既存の予想IDを引き継ぐ。これは初回予想時作成の原則に対する移行時だけの例外とする。mainの過去コミットを削除・書換えず、以降の更新と回顧だけを作業ブランチへ保存する。

### 6.8 発走時刻の誤認とsnapshot保存漏れの是正

#### 6.8.1 事象・原因分析・責務

報告された事象は「タスク開始時刻を発走時刻として扱い、保存しなかった」である。原因仮説は、時刻の意味と出所が未分離であったこと、発走前適格性の判断から保存そのものの省略へ直結したこと、回答前に未保存を検出できなかったことである。実装時に事故時の入力・時刻根拠・判定・保存呼出しの有無を確認する。ログがなければ仮説を確定原因と記載しない。

時刻と保存判断の正本は `00_core.md` に集約し、manual READMEは入口、snapshot READMEは保存形式・参照先、validationと50_reviewは事故記録・KPI判定を担当する。注意書きだけでは完了とせず、下記の必須項目・判定表・回答前照合をチャット実行手順へ組み込む。既存の書込処理がある場合は同じ入力検査を適用し、将来システムの実装待ちにはしない。

#### 6.8.2 時刻の定義と取得元

| 項目案 | 意味・許可する取得元 | 用途 |
| --- | --- | --- |
| task_started_at_jst | 当該タスク開始の実測時刻。取得できなければ不明 | 作業時間・障害調査のみ。発走済みの根拠には使わない |
| scheduled_post_at_jst | 対象レースの公式出馬表・開催情報にある発走予定日時 | 発走前判定の基準 |
| effective_post_at_jst | 公式に確認できた変更後の発走予定日時。変更がなければ確認済みの予定日時 | 遅延・変更時の比較基準。推測で延長しない |
| post_time_source | 取得元URL、開催日・競馬場・Rまたはrace_id、原文の時刻、現地タイムゾーン、取得時刻 | 発走日時の同一レース照合と出所監査 |
| checked_at_jst | 判断直前に時刻取得機能または実行環境の時計から取得した現在日時 | 発走予定日時との比較。タスク開始時刻・情報取得時刻を代用しない |
| fixed_at_jst | 正式内容を固定した実測日時。既存の同名項目を使用 | 内容の固定時点 |
| information_cutoff_jst | 使用情報の締切。既存の同名項目を使用 | 未来情報混入の確認 |
| persist_requested_at_jst / readback_verified_at_jst | 保存要求・読戻し一致を実測した日時 | 保存完了の証跡。コミットの任意設定可能な日時だけで代用しない |

日時は日付・時刻・UTCオフセットを含む形式（例：`2026-09-22T15:40:00+09:00`）に統一し、時刻だけで比較しない。海外レースでは出典の現地日付・タイムゾーンを保持して変換する。日次ブランチの作業日は発走日時の代替にしない。

発走日時は主催者公式を優先する。取得不能なら対象レースを照合した利用可能な代替情報源を確認し、代替利用を明示する。時刻が矛盾する、対象が一致しない、タイムゾーンが不明、必要な精度の現在時刻が得られない場合は未判定とする。タスク開始・チャット送信・予想固定・オッズ更新の時刻を発走日時へコピーしてはならない。

発走前の適格性判定では、結果・着順を既に知っている、実際の発走を確認済み等の証拠がある場合も除外する。未来の予定日時だけで、そのような内容を適格化しない。全体選別の一括保存でもレース別に判定し、発走前の対象と遅延・未判定の対象を分離する。

開始時に対象レースと発走日時を確認し、正式固定・保存の直前に現在時刻を取得して比較する。境界到達・変更情報・出典間矛盾がある場合は、締切内で発走予定の変更を確認する。再取得を無制限に続けない。タスク開始と発走予定が偶然同じでも、値の一致だけで誤りと判定せず出所で区別する。

#### 6.8.3 保存判断と適格性を分離する

次の2軸を独立に保持する。

- 保存状態：未試行／要求済み／読戻し一致／保存失敗／読戻し未確認。
- 発走前証跡の状態：適格／未判定／不適格。保存成功だけで適格へ昇格させない。

| 確認状況 | 保存動作 | 発走前証跡の扱い |
| --- | --- | --- |
| 現在時刻が根拠付き発走予定より前で、正式内容が固定済み | 日次ブランチのsnapshotsへ直ちに保存し、同じブランチから読戻す | 固定・保存・読戻しが発走前で、情報締切等の既存要件も満たした場合だけ適格 |
| タスク開始時刻が過去だが、実際の発走予定は未来 | 上記と同じ。タスク開始時刻を理由に省略しない | 正常な発走前保存として確認する |
| 発走日時または現在時刻が未確認・矛盾あり | 限定した再確認を行い、解消しなければ既に固定した内容と時刻の不足を未判定記録として保全 | 未判定。発走済みとも発走前とも断定しない |
| 確認済みの予定日時と同時刻またはそれ以降で、延長の公式根拠なし | 既に固定済みの内容は遅延記録として保全。新規の発走前snapshotを偽装しない | 不適格または実際の発走状況未確認。結果未取得だけでは適格にしない |
| 保存要求時は発走前、読戻し確認は境界以降または失敗 | 同一IDの実保存有無を確認し、既存snapshotを消さず保存状況を事故記録に残す | 発走前読戻し完了を証明できなければ適格としない |
| GitHub保存に失敗 | 現行の最大1回の再試行とfail-softを維持し、同じ正式内容と失敗状態をチャットへ提示 | 保存済みと表現しない。復旧が発走前ならsnapshot保存を再開し、発走後・未判定なら別記録へ保全 |

本書の「遅延」は回答前の保存順序違反と発走締切超過を区別する。回答後でも確認済みの発走前であれば、固定済み内容を変更せずsnapshotsへ保存・読戻しを実施する。順序違反の事実は別途記録し、発走前保存・内容充足・KPI適格性は各証拠から独立に判断する。

未判定・発走締切超過・保存事故の管理記録は `docs/validation/records/` の当日記録内の専用節へ保存する案とし、正常な発走前snapshotと区別する。対象日と予想ID、固定済み内容、使用情報の締切、発走日時の根拠または不足、保存状態、原因コードを保持する。回顧・結果を固定済み内容へ混ぜない。既に固定済みの内容がなければ捏造せず事故情報だけを記録する。既にsnapshotsへ書き込まれていた場合は削除せず、事故記録から参照する。

未判定記録は前向きKPIへ自動算入しない。後から予定時刻を取得しただけでは発走前保存済みにしない。訂正する場合は当時の固定・リモート保存・読戻しを証明する独立した証跡を示し、既存のOwnerの審査規定で判定する。

この方針は「正式内容の保全」と「発走前証跡としての適格性」を分けるものであり、結果後に予想を作り直してsnapshotへ入れることを許可しない。

#### 6.8.4 回答前の必須照合

正式固定した出力ごとに、次を照合してから最終回答へ進む。暫定分析だけの段階を無理にsnapshot化しない。

1. race_idと発走予定日時の根拠が対応し、タスク開始時刻が発走判定の入力に入っていない。
2. 比較した現在日時と発走予定日時を保持し、未判定を「発走済み」へ変換していない。
3. 保存先ブランチ、パス、snapshot_idまたは事故記録の識別子が定まっている。
4. 保存呼出しと結果がある、または実際の障害によって試行できなかった理由がある。「発走済みと思ったため未保存」だけで完了にしない。
5. 正常保存は対象ブランチから読戻してIDと主要内容が一致し、コミットSHAが引継ぎ情報にある。
6. 保存失敗・未判定・遅延は具体的に報告し、該当する記録・未完了事項を残す。回答前照合を理由に予想回答を無期限に止めない。

原因コード案は `POST_TIME_UNVERIFIED`（未確認）、`POST_TIME_SOURCE_MISMATCH`（出所・レース不一致）、`POST_TIME_CONFLICT`（矛盾）、`CLOCK_UNVERIFIED`（時計未確認）、`SNAPSHOT_SAVE_OMITTED`（保存漏れ）とする。既存の保存失敗・読戻し失敗コードとは併記し、同じ意味のコードを重複定義しない。

#### 6.8.5 今回の事故の補正と有効性確認

事故対象が特定できる場合は、レースID、正しい発走日時の出典、誤用したタスク開始日時、予想固定日時、実際の保存呼出しと結果を確認する。第4版では対象日snapshotを読み、10Rの時刻誤認と12Rの保存未試行を特定した。チャット全ログ・当時の保存呼出し・読戻し履歴までは確認できていないため、事故の補正完了やKPI適格性の確定とは扱わない。

未保存の固定済み予想がチャットに残っていれば、内容を変更せず遅延記録へ保全する。元のチャット時刻と後日のGit保存時刻を区別し、発走前Git保存の捏造や結果に合わせた改変は行わない。対象を復元できない場合は不明の項目と理由を記録する。

実装後はタスク開始日時だけを変更しても、発走日時と保存直前日時が同じなら保存判断が変わらないことを回帰検証する。次回の実予想でも固定済み出力と保存記録を突合し、未試行・未報告が0件であることを確認して有効性を判定する。注意文の追加だけで再発防止完了とはしない。

| 工程漏れ・未試行 | FIXEDなのに保存呼出しも実行不能の根拠もない | 発走前なら直ちに保存工程へ戻る。順序違反を別記録へ残す |

例外時も無期限に回答を止めず、根拠付きの状態を示す。ただし「忙しい」「時間がないと思った」「締切を過ぎたはず」は例外の証拠にしない。確認した現在日時・発走日時と実行状態から判断する。

`PRE_RACE_SNAPSHOT_PERSIST_FAILED` は保存処理を実際に試行して失敗した場合に限定する。工程漏れは既存案の `SNAPSHOT_SAVE_OMITTED`、機能利用不能で未試行の場合は別の実行不能理由で表す。同一ID・同内容が既に保存されている正常系は新しい書込を要求しない。タイムアウト後に読戻しで同内容を確認できた場合は重複追記しない。

開始プロンプト・チャット実行手順にこの順序を組み込み、実在する保存処理に検証可能な呼出し結果を残す。実行基盤にない強制機構を実装済みと称さない。利用可能な検査処理と実行リハーサルにより検出を確認し、単なる「必ず保存する」の再掲で完了としない。

#### 6.9.3 12Rの時刻矛盾を補正する計画

次の3軸を独立に扱う。

1. **回答前保存手順の遵守**：保存・読戻しより先に回答したなら違反。
2. **発走前のGit保存・読戻し証跡**：確認した発走日時とリモートの履歴・読戻し記録から判定する。
3. **KPI適格性**：必須内容、情報締切、証拠の有無をKPI別に判定する。

12Rの16:02と16:10が正しければ、保存記載時刻は発走より8分前である。「回答後だから発走後保存」とはできない。一方、本文に書かれた保存時刻だけでは当時のリモート保存・読戻しを証明しないため、現時点で適格とも断定しない。コミット・変更差分、当時の読戻し、元チャットの固定・回答時刻を照合し、確認不能部分は未確認とする。コミットの任意設定可能な日時だけに依存しない。

10Rも「最初は誤報告」と「発走前に訂正保存したとの記録」を併記する。誤報告だけで最終的な保存失敗とみなさない。今後、発走前に復旧できた内容はsnapshotsへ保存し、回答順序違反の管理情報をrecordsへ分離する。

過去の不変snapshotを上書きして整合させず、`records/2026-09-22.md` 等に元のID・参照箇所・誤記・確認した証拠・訂正判断を追記する。今回の計画更新ではこの補正処理自体は実施しない。

#### 6.9.4 必須項目・参照・取得証跡の検証

- 全体選別の1エントリに複数レースを含めてよいが、各レースの必要情報と参照を解決可能にする。朝の全体snapshotにIDを付け、個別更新は当該レースを含む先行エントリへ参照させる。

- 欠けた確率や監査値を結果後に推測で補完しない。保存前に存在する証跡への参照を解決できなければ詳細不足とし、保存可能な固定内容は保全しつつ不完全なものを正式完了・KPI適格としない。

#### 6.9.5 購入監査とShadowの証跡

30_betting 48.2.1の既存項目を正式買い目の固定前に確認する。主要券の成立確率・合理的レンジ・レンジ下側の評価、最大馬依存額/率、軸崩れシナリオ、監査後判断・理由を保存本文または不変の参照先へ残す。「完了」の一語で代替しない。

10Rの固定10,000円案は、5を含む買い目が合計8,000円で依存率80%となる。券種を馬連とワイドへ分けても同じ馬への依存は解消しない。11Rも記録上の12依存は80%。80%を新しい禁止閾値にはせず、既存ルールで維持・配分変更・総投資削減・見送りを判断した証拠を要求する。実購入900円/2,200円は固定10,000円案と別帳簿のまま計算する。過去の推奨を結果後に変更しない。

Shadowは適用判定、完了／未完了／非該当、理由と出力の所在を記録する。「使用せず」や「Productionへ逆流なし」だけでは、実行完了の有無は判定できない。対象該当性が不明なら不明、工程失念なら未完了とし、非該当へ置換しない。Shadowの不備だけでProductionを無効化しない。

#### 6.9.6 実装順序・完了判定

00_core・snapshot README・validation README・30_betting・50_review・現行チャット開始手順の直接関係する記述を整合させる。予想評価式の変更、新しい馬依存率閾値、実購入の自動操作は追加しない。snapshotへの既存の実購入追記契約は維持し、事故分類・結果後の分析はrecordsへ分ける。

#### 6.9.7 成否不明・時間配分・再開の補足

- 保存要求がタイムアウトした場合は「要求済み・成否不明」とする。呼出し時刻・対象branch・path・ID・応答を保持し、まず同じIDを読戻す。保存済みなら再追記せず、成否不明を根拠なく失敗確定へ変換しない。
- 書込成功後も、読戻し未実施は「未確認」、読戻しを実際に試してエラーや不一致が出た場合は「読戻し失敗」と分ける。成功応答だけで正常完了としない。
- 正式FIXかつ保存未試行なら保存工程へ戻す。投資額0円、基準予想のREUSED、短い回答指定、タスク開始時刻を保存省略の理由にしない。
- 開始時と正式固定前に残り時間を確認し、追加取得・再分析の打切りは保存・読戻しに必要な時間も含めて決める。根拠なく固定の秒数を設定せず、利用中の経路の所要時間と実測した現在日時を用いる。追加取得を打ち切っても、未試行の保存を失敗と称して飛ばさない。
- 実行票・引継ぎ票には、対象repository・branch・path・snapshot ID・固定内容・時刻根拠・保存要求の有無・結果・読戻し状態・commit SHA・未完了工程を保持する。分析途中のGit保存は追加しない。commit SHAはAPI応答から引継ぎ票へ保持し、その同じcommit本文へ埋め込もうとしない。
- 馬体重の「未発表」はその根拠がある場合だけ使う。検索抜粋の空欄、古いページ、動的値未取得、アクセス拒否を区別し、公式→スポーツナビ→他の信頼できる当日情報の既存取得手順に沿って試行する。代替で全頭取得できた正常系では、公式未照合を明記しつつ取得成功として継続する。
- これらは現行チャットの手順・実在する保存操作に対する是正計画である。未実装のシステムによる強制や未接続の取得手段を実現済みとしない。

## 9. セルフレビュー観点

- owner未記載と、検索後も対象を特定できない状態を区別できているか。
- 取得前の入口が機能し、READMEが現行ルールの正である関係を維持しているか。
- READMEから必要なProductionルールへ到達でき、将来仕様とShadowが混入しないか。
- 「問題がある場合だけ報告」が、必須の監査・欠落・保存失敗の隠蔽に使われないか。
- 新しい承認待ち、必須入力、分析途中の保存義務を不要に増やしていないか。
- 評価式、買い目、ルール昇格、既存記録、ProductionとShadowの境界を変更していないか。
- 予想・回顧の全書込先が日次ブランチとなり、再開時の読込も同じブランチになっているか。
- 翌日の回顧、並行チャット、途中移行でブランチの重複や記録の上書きが起きないか。
- 発走前の永続化がPRマージ待ちになっていないか。

- タスク開始・発走予定・現在・固定・保存確認の時刻が分離され、発走日時の根拠が照合されているか。
- 時刻未判定や発走後を保存省略へ直結させず、遅延記録と適格性を区別しているか。
- 00_coreとsnapshot READMEのmain限定保存条件が日次ブランチ案と同時に修正されるか。

- 回答後保存を発走後保存と混同せず、未試行の保存失敗コード誤用を検出できるか。
- 必須項目・購入監査・Shadowの宣言と実際に確認できる証跡が一致するか。

## 10. 完了条件と切り戻し

以下を満たした時点で是正実装の完了とする。

1. R1～R18が実装され、入口・正本・関連手順の整合が取れている。
