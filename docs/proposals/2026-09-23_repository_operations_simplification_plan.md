## 最優先: 発走前に予想と検証材料を失わない

前サイクルでは、リポジトリ参照による停止、発走時刻の取り違え、保存工程の抜け、必須比較の未固定、日別とサイクル集計の不一致が実際に記録された。現行の`00_core`には障害時も予想回答を遅らせない規則があるが、実レースで初回→最終→回顧・集計が正常に一巡した証拠はまだない。文書の整理より先に、下記の締切内の経路を試す。

1. **依頼直後の限定的な事前確認**: 公式の対象レース・発走予定時刻、同一commitの必要ルール、既存基準予想と元の日次branch、Gitへの読み書き経路を確認する。独立取得は同時に行い、接続や補助情報を無制限に待たない。Gitの一経路に失敗しても、別経路で同じ現行mainの正式ファイルを確認できる場合だけ正式に継続する。以前確認済みのルール一式だけでは現行mainと一致するとみなさない。必要ルールを確認できなければ正式な予想と称さず、その不足を直ちに伝える。将来、版を固定した控えを代替に使うなら、事前の有効期間・更新検知・表示上の扱いを別途審査する。
2. **時間配分と早期の固定**: 確認した発走予定時刻から逆算し、入力取得、正式予想、保存・読戻し、利用者への送信に必要な時間を確保する。残時間が縮まれば補助取得や追加分析の再試行を先に打ち切り、確定できたProductionを早めに固定する。初回snapshotを先に残し、最終予想では既存の静的情報を再利用する。正式にFIXEDした内容は現行の不変snapshot/receipt契約に従って保存し、比較・買い目の不足は成果物ごとに区別する。
3. **障害時の出口**: 保存や読戻しが間に合わなくても、発走前に確認できた内容を状態に即した名称で回答する。監査未完了の買い目を確定買い目と表示しない。実際に保存できたか不明なら同じIDを調べ、再試行は既存の回数制限に従う。発走後は元のFIXED内容をpreservationへ保全し、発走前のGit証跡を後付けした扱いにしない。
4. **再開と回顧**: 別チャット・翌日でも元branchの初回snapshot・候補台帳・receiptを確認してから続ける。保存失敗や未実施のレースも、利用可能な発走前記録と欠測理由を回顧へ残す。Git本体・receiptが現行適格条件を満たさなければ該当KPIは不適格または保留とし、チャット回答だけで適格化しない。
5. **サイクルの閉じ方**: 欠測した日があっても、対象全件の実施/未実施、証跡と欠測理由、KPI別適格性、次回への再試験を確定して終了審査を行う。サンプル不足の仮説は判断保留・継続検証にし、成果なしと断定しない。「運用上の終了」と「仮説の有効性を判定できたこと」を分ける。

GitHub全経路が使えず、発走前の本体とreceiptを確認できない場合、現行契約のままでは前向きKPIを適格にできない。予想の送信、失われた証拠の保全、欠測を明記したサイクル終了は可能だが、適格な比較数は保証できない。別の永続証跡を適格にする変更が必要なら、事後的な結果に影響されない要件と同等の時刻・内容確認方法を別PRで審査する。

## 整理後の責務

1. `docs/manual/README.md`: チャットの入口と読み込み先。予想・買い目・回顧の詳細定義を複製しない。
2. `00_core`: 対象集合、時点、実行順、引継ぎ。`10_prediction` / `20_conditional` / `30_betting` / `40_shadow`: 各判断・比較の唯一の定義。`50_review`: サイクル登録、KPI適格、回顧と集計の完了条件。
3. `docs/validation/README.md`: 現行サイクルの索引と状態。snapshot・receipt・日別recordの書式や読戻しは各運用README、記入欄はテンプレートに置く。サイクルファイルには計画と実測を区別して残す。
4. `docs/proposals/`: 作成当時の調査・計画の履歴。現行ルールをここから再定義しない。第2サイクルの確定前データと監査根拠は、終了審査が済むまで保持する。

## 実施順

### 0. 発走前の一巡と故障時の経路を先に検証

- G0で「通常の初回依頼→候補の最終依頼→回顧依頼」だけを使い、現行の参照・予想・買い目監査・本体/receipt読戻し・日別/サイクル集計までを、隔離した模擬データと許される実I/Oで通す。従来の机上PASSを実行合格に読み替えない。
- 安全に再現できるGitの競合、遅延・成否不明、receipt未確認、元branch/既存予想が見つからない状況、公式時刻未確認、動的情報の欠測、必須比較の時間不足、同時刻帯の複数レース、別チャット/翌日の再開をそれぞれ確認する。実I/Oができない故障ケースは机上に留め、未試験を一覧化する。
- 予想を発走前に送信したか、各成果物の保存状態、KPI適格性、追加督促回数、日次→サイクル集計完了を別々に記録する。異常を正しく報告できたことと、全工程の正常完了を混ぜない。
- 第3サイクル最初の実レースを余裕を持って開始する確認対象にし、実運用の所要時間と欠測を測る。G0未完了や重大停止が残る場合は通常予想を一律停止せず、対象と限界を明示して安全な経路だけを実行する。

### 1. 参照と状態の整備

- 上記Owner表に沿って重複箇所・リンク・版・「適用中/履歴」を一覧化し、現在の入口にある古い状態表示を正す。
- `40_shadow` の旧サイクル優先順位・過去の具体例は、現行の適用条件と区別する。削除前に現行manual・検証記録からの参照を確認する。識別子とGit履歴を切断しない。
- ここでは予想の順位、確率、券種・配分、Shadowの適用条件、保存適格条件は変更しない。

### 2. 予想から回顧への引継ぎを一本化

- 初回の候補台帳、最終の未取得一覧、保存本体と確認証跡、回顧の対象集合を、Ownerとテンプレートの対応表で追えるようにする。同じ内容の二重記入をなくし、参照先を固定する。
- 正常な最終対象外、未依頼、工程未実施、取得不能、保存成否不明を別状態で引き継ぐ。簡潔な回答でも必要な内部工程を省略しない。
- snapshotは発走前の不変記録、receiptは読戻し・時刻適格性、recordは結果後の評価という境界を維持する。

### 3. 日別集計とサイクル集計を照合可能にする

- 各日別recordから対象race_id集合・KPI別の対象/適格/不適格/保留、投資・払戻、参照commitを集計する。同一日の再実行はrevisionを置換し、加算し直さない。
- 集計の検証を軽量なチェックで再現可能にする案を検討する。最低限、集合の重複・欠落、相互排他、snapshot/receipt参照、帳簿の混同、日別/サイクルの合計、別日PR統合時の上書きを検出する。実装形式は既存Markdownから無理なく検査できるかを先に小規模に試す。
- 自動化を導入しても外部レースデータ取得や予想判断は代行しない。検証不能な値を0や成功へ補完しない。

### 4. 第2サイクルを閉じて次回へ引き継ぐ

- 第2の集計は当時の契約と証跡をレースごとに監査して確定または保留とする。過去のsnapshot・買い目を結果から作り直さない。
- サイクル終了時は各仮説を昇格/継続検証/棄却/判断保留に分類し、適格件数、比較結果、欠測、非劣化、判断理由、参照commit、次回の取得条件を引継ぎ欄に残す。未実行を効果なしと判定しない。
- 正式ルール変更は審査後の別PRとし、現行サイクルが参照する文書や未終了データを一括削除しない。

## 受入条件

- 初回24Rから検証4R・購入3R（重複2R）を選ぶ例で、最終対象5R・回顧対象24Rを維持し、候補外19Rを最終欠測へ数えない。
- 同じレースを別チャット・翌日・別branchで再開しても元の基準予想と証跡を参照でき、未確認なら推測で再生成しない。
- 本体未保存、receipt未確認、発走時刻不明、結果未確定、Shadow未完了について、回答・KPI・回顧・一巡成功を独立判定できる。
- 日別のrace_id×KPI集合とサイクル合計が一致し、再実行・複数日PRの統合で重複加算・上書きがない。
- 第2の正式KPIと第3の実績を分け、保留・未測定・実測0を区別する。机上試験と実レースLIVEも混ぜない。
- 利用者向けの回答は予想・買い目・回顧・進捗の依頼に必要な内容に絞り、追跡用IDの説明を要求しない。
- 変更は作業ブランチから個別PRで行い、各PRで変更の本質をセルフレビューする。確認だけに作成した一時ファイルは含めない。
- 公式発走時刻とタスク開始時刻を取り違えず、遅延する外部取得・保存経路を打ち切り、発走前に状態を正確に伝えられる。残時間不足で正式予想が成立しない場合も原因と未完了工程を隠さない。
- Gitの明示失敗、要求後の成否不明、receipt未確認、時刻不明、既存予想回収不能を別状態として再開でき、同じIDの二重保存や別の正式予想の無言再生成がない。
- Production、買い目、各比較の保存と適格性を独立に判定でき、いずれかの欠測を他へ誤って連鎖させない。見送りと検証用のみも台帳・回顧から消さない。
- 実レースでの初回→最終→回顧→日別・サイクル集計が追加督促なしで成立した場合だけ運用上の一巡成功と記録する。部分試験は部分試験のまま残す。
- 適格サンプルが足りなくても、対象集合と未実施・不適格・保留、次回に必要な取得を確定してサイクル終了審査を行える。

## 実施上の境界

本計画は設計・整理の提案であり、実レースの予想、過去成績の再確定、第2サイクル終了審査、現行ルールの昇格を実施した記録ではない。チャット環境がリポジトリを自動的に読む保証はないため、プロジェクト側には「`eda-hub/horse-man` の `main` の `docs/manual/README.md` と必要なOwnerを毎回参照する」という短い入口指示を残す。
