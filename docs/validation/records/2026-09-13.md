# 2026-09-13 予想・購入回顧（進行中）

- **位置づけ**: v1.6.1前向き検証日
- **記録状態**: 開催中の暫定記録。確定結果後に追記する。
- **重要インシデント**: 阪神8R FINAL直前の当日馬体重取得失敗

## 1. データ取得インシデント — 阪神8R

### 事象
発走約10〜20分前のFINAL予想作成時、予想側のWeb取得経路では当日馬体重を取得できず、外部馬柱が `---kg` 相当の未取得状態として見えた。

一方、ユーザーが確認しているnetkeibaのブラウザGUIでは同時刻に当日馬体重が表示されていた。

### 判定
これは「馬体重未発表」ではなく、**予想側の取得経路がJavaScript等で動的描画された最新値を取得できなかったデータ取得障害**として扱う。

分類は、予想ロジックの誤りではなく **外部データ取得・時刻整合 / SOURCE_ERROR** とする。

### 禁止する誤対応
- 静的HTMLで空欄だから未発表と断定する
- 前走馬体重を当日馬体重として代用する
- 推測値をFINALへ入れる
- 結果後に取得できた値で固定済みFINALを上書きする

### 初動改善
インシデント直後は、FINALのT-20 readiness gateで馬体重を再取得する方針を設計へ反映した。

- JRA-VAN/JV-Link速報WHを一次取得元とする
- JRA公式一次情報を照合・フォールバックに使う
- 外部Web GUIは補助確認に限定する
- `SOURCE_ERROR` または必須欠損時は `data_readiness=DEGRADED` とする
- 欠損項目、source、最終成功時刻、取得失敗時刻を保存する

ただし、その後の公式仕様再調査により、**「T-20以降の馬体重snapshotをREADY条件にする」という部分は不適切**と判明したため、下記のとおり訂正する。

### 再調査結果
JRA-VANのJV-Data仕様では速報馬体重 `0B11` は通常レース発走約1時間前から提供される。またJV-Linkは `JVWatchEvent` により馬体重発表event `JVEvtWeight` を受信でき、その返却keyを `JVRTOpen` に渡して `0B11` を取得できる。

したがって今回の根本問題は、

> **T-20では馬体重がまだ出ていないこと**

ではなく、

> **発表された時点で一次データを捕捉・保存せず、FINAL直前にWeb経路からその場取得しようとしていたこと**

にある。

また季節・競馬場によって計量/発表時刻が通常より遅くなる運用があるため、「必ずT-60」の固定時刻にも依存しない。Event通知を主経路とし、広いfallback windowで補完する。

### 恒久改善
- 開催日は `JVWatchEvent` を常時監視し、`JVEvtWeight` 受信時に `JVRTOpen(0B11, event key)` で即時取得する
- Core Service再起動・Event取り逃し時は `0B11` のrace-key / day-key catch-upで既発表値を回収する
- Event未受信時だけ、予想対象レースをT-75〜T-20の範囲で低頻度pollingする
- T-20は**取得開始時刻ではなくcoverage検証時刻**とする
- T-20より前に取得済みの完全な当日公式WHはFINALでそのまま有効とし、取得時刻だけでSTALEにしない
- 馬体重readinessを `PENDING / READY / PARTIAL / MISSING / STALE / SOURCE_ERROR` に分ける
- `first_observed_at`, `captured_at`, provider timestamp(nullable), source, acquisition methodを保存する
- 取消・競走除外を除く現出走対象馬すべてとのcoverageを確認する
- `JVEvtWeight` 受信済み/JRA公式表示済みなのに内部取得できない場合は `SOURCE_ERROR` とする
- JRA-VAN公式動作確認ツールでも同一 `0B11` を確認し、provider側とAdapter/Parser側を切り分ける

### 設計反映

## 2. 回顧時の確認事項

開催終了後、少なくとも以下を確認する。

- `JVEvtWeight` を正常受信できたレース数
- Event受信からWH保存までの遅延
- catch-up / pollingで救済したレース数
- 馬体重を取得できなかったレース数
- GUI/JRA一次情報表示済みなのに内部取得できなかったレース数
- `PARTIAL / SOURCE_ERROR` の原因内訳
- `DEGRADED` FINALと`READY` FINALの予想精度差
- 馬体重未反映が実際に印・確率・仮想買い目へ影響し得たか

この事象単独を根拠に馬体重評価ルールそのものは変更しない。改善対象はデータ取得とFINAL確定手順である。

## 3. データ出典の偏り — 馬柱・血統・競走データ

### 事象
当日のチャット予想では、リアルタイム馬体重のfallbackにnetkeiba GUIを使用したほか、過去成績・馬柱・調教補助情報でnetkeiba、競馬ラボ等のWeb aggregatorを繰り返し参照した。

これらのサイトを使うこと自体が誤りではないが、次のリスクを確認した。

- 同じJRA由来の競走事実を複数サイトが転載しているだけなのに、独立した複数根拠のように見える
- Webサイト独自の指数・脚質分類・血統分類・調教評価がraw factと混ざる可能性がある
- 取得しやすいサイトの項目だけが説明文に増え、予想根拠の比重が暗黙に偏る
- GUIで取れるためにfallback sourceが実質primary化する危険がある

### 判定
これは単一の誤データではなく、**source provenance / source-count biasの設計不足**として扱う。

予想ルール自体を変更する事象ではない。`docs/manual/` は変更せず、データ取得・provenance設計を改善する。

### 恒久改善
- `docs/jravan/11_source_provenance.md` を新設し、データ種別ごとのPrimary / Secondary / Web fallbackを定義
- JRA-VAN/JRAで取得可能な客観事実は一次情報を通常経路とする
- 血統はJRA-VAN BLDNを主とし、JBIS等をspot checkに使う。系統・インブリード判定は内部再計算する
- 調教時計とメディア主観評価を分離する
- netkeiba等の予想印、AI印、独自総合ランキングをProduction能力評価へ入れない
- `source_class` と `origin_group` を導入し、サイト名が違っても同じ上流なら独立証拠として数えない
- DBに `ops.source_registry` / `ops.data_provenance` を設計し、derived featureからraw sourceへ遡れるようにする
- Phase 2受入条件とテスト仕様にsource bias検査を追加する

### 回顧指標
開催終了後・検証サイクルごとに以下を確認する。

- critical fieldのJRA-VAN/JRA Primary coverage率
- Web fallback利用率
- `UNKNOWN_AGGREGATED` 利用率
- source conflict件数
- 同一origin_groupを複数独立証拠として数えた違反件数
- 第三者指数/予想がProduction evidenceへ混入した件数（0件目標）

馬体重取得問題と同様、**データ取得・出典品質の失敗を予想ロジックの失敗と分離する**。
