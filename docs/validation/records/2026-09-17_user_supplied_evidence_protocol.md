# 2026-09-17 U-02 ユーザー提供情報の事前チャット固定・事後妥当性検証

## 位置づけ

- 対象: 第2検証サイクル
- 開始日: 2026-09-17
- 基準Production: `v1.6.1` のまま変更しない
- 検証種別: 補助診断 / 回顧拡張
- 正式Productionの能力評価・印・確率・買い目ルールへの自動反映: なし
- 将来実装設計: `docs/jravan/14_user_supplied_evidence.md`

目的は、予想前にユーザーがチャットで提供した独自収集情報を、通常の取得情報と混同せずに**発走前チャットで固定**し、結果後の回顧時にGitへ整理して「その情報自体は正しかったか」「予想材料として有効だったか」「どの判断へ寄与したか」を分離して回顧することである。

この検証は、ユーザー提供情報を無条件に強く扱うためのものではない。また、ユーザー本人に一括の信頼度スコアを付けることを目的としない。情報の種類、元ソース、条件、検証可能性ごとに評価する。

## 0. 過去蓄積情報の一括持ち込み — BACKFILL_SEED

U-02開始前からユーザーが蓄積していた条件別知見をまとめて受領した場合は、通常のレース固有事前情報と区別して `BACKFILL_SEED` とする。

- 原文の意味を変えずseed catalogへ保存する。
- 受領時点で元ソース・集計期間・母集団が不明なら `source_origin_status=UNKNOWN`、`precheck_status=UNVERIFIED` とする。
- 過去レースへ遡ってU-02の成功・失敗件数を付けない。
- 今後の該当レースで使用する際は、結果確認前のチャットで採否・影響先を固定し、回顧時にその発走前snapshotを根拠として原子的claimへ分解し `user_evidence_id` を付与する。
- 略号・表記が曖昧なものは推測で正規化せず、原文を保持して `UNRESOLVED_TERM` とする。
- BACKFILL_SEED自体はProductionの正式ルールではなく、前向き検証候補の母集団とする。

2026-09-17受領分は `records/2026-09-17_user_accumulated_heuristics_seed.md` を正本とする。

## 1. 発走前はGitへ保存せず、チャット上で最小限を固定する

ユーザーからレース予想用の情報を受け取った場合、予想中はその記録だけを目的としたGitHub書き込みを行わない。ユーザー原文と、予想回答内での採否・影響を発走前snapshotとして扱う。

予想段階で最低限追跡できればよい情報は次とする。

| field | 発走前の扱い |
|---|---|
| `claim` | ユーザー原文または意味を変えない短い要旨。原文はチャット履歴を参照元とする |
| `supplied_at` | チャットの発言時刻 |
| `horse_or_race` | 対象馬 / レース全体 |
| `upstream_source` | ユーザーが提示した場合は保持する |
| `precheck_status` | 予想上重要で実際に確認した結果だけ記録。未確認なら `UNVERIFIED` 相当 |
| `production_usage` | USED / USED_AS_UNCERTAINTY / NOT_USED |
| `influence_area` | ability / condition_fit / pace / position / state / confidence / betting / none |

`user_evidence_id`、厳密な `evidence_type`、source正規化・重複統合、詳細なfactual/predictive評価は原則として回顧時にチャット履歴から構築する。台帳整形・ID発行・Git書き込みを発走前のクリティカルパスへ入れない。

ただし、Productionへ実際に使ったかどうかと、どの判断へ影響したかは結果前に追跡可能にする。元ソースが不明な情報は捨てないが、独立した複数根拠として重ねない。

## 2. 情報種別を分ける

### FACT

例:

- 距離変更
- 騎手変更
- 過去レースの着差
- 調教時計
- 馬体重

確認可能な事実は可能な範囲で公式・一次情報と照合する。

### OBSERVATION

例:

- パドックで落ち着いて見えた
- 前走より馬体が良く見えた
- 返し馬の反応が良かった

観察自体を「正誤」だけで処理せず、その観察が後のパフォーマンスと再現的に対応したかを蓄積する。

### COMMENT

例:

- 調教師・騎手コメント
- 取材記事の発言

原発言者と転載者を可能な限り分離し、同一コメントの複数転載を複数証拠として数えない。

### INTERPRETATION

例:

- 1600mへ戻る今回は前走より能力を出しやすい
- 距離短縮で先行力が活きる
- 今回の馬場なら末脚を使いやすい

事実そのものではなく、事実から導いた解釈として保存する。

### FORECAST

例:

- この馬は2着まで来る可能性が高い
- この馬は展開利を受ける

第三者予想印・総合指数等をProduction能力根拠へそのまま混入させず、研究・比較情報として区別する。

## 3. 発走前の扱い

ユーザー提供情報は、チャット予想時に次の順で扱う。

1. `docs/manual/` の通常Production分析を優先する。
2. 現行manualの既存評価項目に該当する場合のみ、その既存項目の証拠として利用する。
3. Productionへ使う場合は、回答内で採用したclaimと影響先が追跡できるようにする。
4. 確認可能な事実の照合は予想判断へ重要なものを優先し、台帳を埋めるためだけの追加照合は行わない。
5. 元ソースが分かる場合は保持し、同じ上流情報の重複を数えない。
6. 検証不能または競合する情報は、推測で真偽を確定せず不確実性として扱う。
7. 予想中は記録目的のGit更新を行わない。詳細なevidence recordは回顧時に発走前チャットから構築する。
8. 第2サイクル中は、過去のU-02成績だけを理由にProductionの正式な重み・閾値を変更しない。

## 4. 回顧では「事実の正確さ」と「予測への有効性」を分ける

各 `user_evidence_id` を結果後に最低限次の2軸で採点する。

### factual_validity

- `CONFIRMED`: 内容が事実として確認できた
- `PARTIAL`: 一部は確認できたが表現・範囲にズレがあった
- `REFUTED`: 事実として誤りだった
- `UNVERIFIABLE`: 回顧時点でも確認不能
- `NOT_APPLICABLE`: 主観観察・解釈等で事実判定になじまない

### predictive_relevance

- `POSITIVE`: その情報が示した方向と実際の能力発揮・展開・状態が整合した
- `NEUTRAL`: 情報自体は妥当でも今回結果への寄与が確認できない
- `NEGATIVE`: その情報が示した方向と実際のレース内容が明確に反した
- `UNRESOLVED`: 不利・事故・展開等で妥当性を評価しにくい
- `NOT_APPLICABLE`: 予測的意味を持たない事実情報

重要なのは、**事実が正しいことと、予想材料として強いことを同一視しない**ことである。

例:

- 「1600mへ戻る」は `factual_validity=CONFIRMED`
- 「1600mへ戻れば能力上限が再発現する」は別途 `predictive_relevance` を評価する

## 5. 予想への寄与も分離する

情報が正しかったとしても、Productionへどう影響したかを残す。

- `HELPFUL`: 順位・確率・シナリオ・確信度・買い目の改善方向へ寄与
- `NEUTRAL`: 採用したが結論へ実質影響なし
- `HARMFUL`: 過大評価・過小評価・誤ったシナリオ固定へ寄与
- `NOT_USED`: 受領したがProductionには使用しなかった

結果だけから寄与を決めず、発走前チャットで固定した `production_usage` / `influence_area` と照合する。

## 6. 今後の予想材料への反映

U-02の履歴は、ユーザー本人を一つの信頼度で評価せず、原則として次の粒度で集計する。

```text
evidence_type
× upstream_source / origin_group
× 情報テーマ
× 条件
```

情報テーマの例:

- 調教
- 馬体 / パドック
- 距離適性
- コース適性
- 陣営コメント
- 成長 / 上昇度
- 位置取り / 展開
- 不利・前走内容

複数レースで `CONFIRMED + POSITIVE` が再現する情報系統は、将来の予想で確認優先度を上げる候補にする。

一方、`REFUTED` や `NEGATIVE` が多い情報系統は、即時に無視するのではなく、

- 元ソースの取り違え
- 条件依存
- 解釈の飛躍
- 同一情報の重複
- 観測タイミング

を確認し、必要なら `VERIFY_FIRST` / `LOW_WEIGHT_SHADOW` のような扱いを検討する。

正式なProduction重み変更は、単発では行わず、`50_review.md` の昇格基準に従う。

## 7. U-02診断指標

第2サイクルでは正式主KPIと分離し、次を補助集計する。

- ユーザー提供情報件数
- evidence_type別件数
- precheckでVERIFIED / PARTIAL / UNVERIFIED / CONFLICTとなった割合
- factual_validityの構成比
- predictive_relevanceの構成比
- production_usage別のHELPFUL / NEUTRAL / HARMFUL
- upstream_source / 情報テーマ別の再現状況
- ユーザー提供情報を使ったことでProduction順位・確率・シナリオが変わった件数
- その変更が結果評価上改善 / 中立 / 悪化だった件数

件数が少ないカテゴリは率だけで評価せず、分母を必ず併記する。

## 8. 後知恵防止

- 事前情報の一次参照元は発走時刻より前のユーザー発言と予想回答とする。回顧では結果評価を始める前に対象チャットから事前snapshotを抽出して固定する。
- 結果後に「実はこういう意味だった」とclaimを書き換えない。
- 結果後に初めて見つけた情報はU-02の事前情報として採点しない。
- 当たった情報だけを残さず、採用しなかった情報・外れた情報も発走前チャットで確認できる範囲で同じ形式に整理する。
- 発走前チャット履歴を参照できない場合、結果から事前情報を復元せず `PRE_RACE_SNAPSHOT_UNAVAILABLE` とする。
- レース結果だけで元ソースの一般的信頼性を決めない。

## 9. 標準フロー

```text
ユーザー情報受領
→ 通常の予想処理を優先
→ 採用/不採用と影響先を発走前チャットで固定
→ Production / Shadow / 買い目をチャットで固定
→ 予想中はGitへ書き込まない
→ 発走・結果確定
→ 回顧開始時に発走前チャット履歴からsnapshot抽出
→ user_evidence_id付与・情報種別分類・source正規化
→ factual_validity評価
→ predictive_relevance評価
→ Production寄与評価
→ レース記録 / U-02台帳 / 検証記録をGitへ一括保存
→ 情報テーマ / 元ソース別にサイクル集計
→ 十分な前向きサンプル後に正式ルール化を審査
```
