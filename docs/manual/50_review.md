# 50_review — 回顧・検証・変更管理

結果確定後の回顧、誤差分類、検証サイクル、昇格・降格、変更履歴を管理する。過去レースのProductionを結果に合わせて書き換えない。

> **モジュール契約**：定義の正本は本ファイル内の担当範囲だけに置く。他モジュールの定義は再記述せず、ルール番号または出力名で参照する。`manual_release` が必須依存モジュール間で一致しない場合は処理を開始せず、版不整合として扱う。

## 0.7 ルール更新を凍結期間方式へ変更する

基本予想は回顧のたびに更新しない。

v1.4.0で確立した予想生成の基本骨格を基礎とし、第1サイクル終了審査で購入構築・監査・運用ガードを統合したv1.5.0 基本予想を維持し、v1.6.1を現行基準運用ファイルとして、**原則2週間を1検証サイクル**とする。JRAが土日3場・各12Rを開催する通常形を基準にすると、1開催日最大36R、2週間で最大約144Rとなる。**第2検証サイクルは2026-09-12を改訂・検証起点とし、v1.6.1の前向き有効性評価は2026-09-13以降を対象とする。実開催は中山・阪神の2場開催で、前向き対象は9月13日・19日・20日と、9月21日阪神＋9月22日中山代替開催で構成されるため、対象競走数の上限は合計96Rとする。9月22日は9月21日中山分の移動であり追加開催ではない。** 実際の開催数・中止・海外競馬等により対象数が異なる場合は、発走前snapshotを固定でき、回顧時にその内容を追跡できたレース数を正式なサンプル数とする。

検証の基本単位は次のとおり。

- **第1サイクル：約144R** — 問題発見・検証候補の収集
- **第2サイクル：前向き対象最大96R / 累計最大約240R** — 第1サイクルで見つかった傾向の再現確認
- **第3サイクル：通常2週間なら累計最大約384R** — 改訂候補の総合審査

**各サイクル終了時に必ずルールを変更するわけではない。** サイクル終了は「変更時期」ではなく「変更の必要性を審査する時期」とする。

原則として、第1サイクル終了時は予想生成の基本骨格を維持し、改善候補を検証中ルールへ整理する。ただし、予想生成そのものではなく、**情報取得バグの防止・順位保全・購入候補生成・相関リスク監査・非劣化ガード**のような運用／監査ルールについて、複数開催で同一失敗が再現し、既存基本予想の正常部分を壊さないことが確認できた場合は、第1サイクル終了時でも基本監査 / 基本運用規約へ統合してよい。第2サイクルでは今回昇格項目の非劣化と再現性を重点確認する。

サイクル中に得た改善は検証ログへ蓄積し、基本予想へ即反映しない。

例外として、

- 明確なデータ取得バグ
- 数式・確率の明確な論理矛盾
- 重複ルールによる二重計上
- 安全性・運用上の重大欠陥

のみ緊急修正を認める。

緊急修正も変更履歴へ理由を残し、予想成績の改善を目的とした事後的な調整とは区別する。

## 0.7.1 検証データのライフサイクル

検証ルールの**定義**と、各サイクルで生成される**実データ**を分離する。

- 検証中ルール・比較ロジックの定義：`40_shadow.md`
- 進行中サイクルのShadow結果・比較差分・集計：`docs/validation/`
- 結果後の誤差分類・昇格/降格判断・変更履歴：`50_review.md`

`docs/validation/` は現行サイクルだけを扱う**一時作業領域**とする。過去サイクルをファイルコピーで残さない。

### サイクル開始時

1. `docs/validation/` を作成する。
2. `README.md` に対象サイクル、基準ルール版、開始日、対象検証ルールを記載する。
3. `cycle_XX.md` にサイクル全体の集計欄を用意する。
4. ChatGPT上の予想では分析途中に `records/` を更新しない。2026-09-20以前は当時のチャット事前snapshot契約を適用し、2026-09-21以降に新規固定する対象は0.14.1と `00_core.md` に従って正式FIXED snapshotだけを発走前に `snapshots/` へ永続化する。結果後の正式回顧は `records/` へ追加する。

### サイクル中

- ProductionとShadowを同一 `baseline_forecast_id` で紐付ける。
- 発走前に固定した比較値と、結果後の評価を分離する。
- 検証結果を`40_shadow.md`へ逐次追記しない。
- 同じデータを複数箇所へ複製しない。
- **正式な結果後回顧・検証は `docs/validation/` 側を正本とする。** 重賞の `docs/yosou/` 個別ファイルは回顧の保存先にせず、過去傾向との当年照合と翌年課題だけを保持する。validation側はKPI・エラー分類・実購入・Shadow差分・反実仮想・非劣化判定など、検証に必要な内容を省略しない。

### サイクル終了時

1. `cycle_XX.md` を集計し、各検証項目を**昇格 / 継続検証 / 棄却 / 判断保留**に分類する。
2. 正式ルールへ反映する内容がある場合は、別PRでOwnerモジュールを改訂する。
3. 必要な変更履歴・判断理由を`50_review.md`または該当ルールの変更履歴へ残す。
4. その後、**`docs/validation/` 配下の当該サイクルファイルを削除する。** 全ファイル削除によりディレクトリ自体がGit上から消えてよい。
5. 過去サイクルの検証データが必要な場合は、Git commit / pull request / tagから取得する。

**サイクル終了後に `docs/validation/archive/` や `old/` を作らない。Git履歴を唯一のアーカイブとする。**

この削除はデータ破棄ではなく、現行ツリーを「現在必要な情報だけ」に保つための運用である。

## 0.7.1.1 2026-09-20以前のチャット事前snapshot契約 — 履歴

本項は2026-09-20以前に固定した対象へ適用した旧契約の履歴である。2026-09-21以降に新規固定する対象には適用せず、0.14.1と `00_core.md` の発走前Git snapshot契約を優先する。

旧契約では、事前予想・最終予想・Shadow比較・買い目確定の途中で記録目的のGitHub書き込みを行わず、発走前の時刻付きチャット回答をpre-race snapshotとして、Gitへの永続化は結果確定後の回顧時にまとめていた。

2026-09-20以前の回顧は次の順序を使用する。

1. 対象レースと、当時存在していれば `baseline_forecast_id` を特定する。
2. 発走時刻より前のチャット履歴だけから、Production順位・確率・予想確信度・主要シナリオ・Shadow差分・市場評価・買い目・ユーザー提供情報の採否を抽出する。
3. 抽出内容を `review_input_snapshot` として先に固定し、結果を見た後で解釈を変更しない。
4. その後に確定結果、払戻、レース内容を確認して通常の回顧を行う。
5. Production / Shadowの結果後評価、KPI、エラー分類、実購入、反実仮想、非劣化判定等を `docs/validation/` の当該レコードへ保存する。
6. 対象が重賞なら `docs/yosou/README.md` に従い、validationの回顧を再掲せず、当該重賞ファイルへ翌年用のレース固有知識だけを反映する。

発走前チャット履歴を参照できない場合は、結果から事前予想を再構成しない。必要な発走前情報を確認できないKPIは不適格または未確認として扱う。

同一レースの事前予想と最終予想で共通する静的情報は `static_evidence_snapshot` として同一入力とみなし、回顧でも重複レコードへ展開しない。時点依存情報は各 `dynamic_evidence_snapshot` の取得時刻を保って比較する。


## 0.7.1.2 重賞回顧の `validation / yosou` 分離

重賞の回顧では、保存目的を次の2層へ分離する。

### A. `docs/validation/` — 正式回顧・検証の正本

次を保存する。

- 発走前Production / Shadow snapshotと適格性
- 確定結果・払戻
- 予想・価格判断・馬券の採点
- 実購入・固定仮想資金の成績
- KPI
- A〜L等のエラー分類
- 反実仮想チェック
- 非劣化判定
- 検証中ルールの改善 / 中立 / 悪化
- 改善候補ログと昇格審査用材料

### B. `docs/yosou/` — 重賞固有の翌年用知識

次だけを残す。

- 過去傾向・レース固有仮説から見て、当年予想がどうだったか
- 当年結果により、どの傾向が継続 / 弱化 / 新規候補 / 例外となったか
- コース・開催条件変更等により過去傾向の転用性がどう変わったか
- 翌年に向けたレース固有の予想課題
- 翌年予想時のチェックリスト

当年の印・着順・レース内容をyosou側へ記載する場合も、**過去傾向との照合に必要な最小限**に留める。実購入収支、KPI、エラー分類、Shadow成績等を再掲しない。

回顧実行時は、

**validationへ正式回顧を保存 → yosouへ翌年用のレース固有知識を抽出**

の順序を固定する。

発走前snapshotが存在しない重賞でも、確定したレース事実による過去傾向更新はyosouへ反映できる。ただし結果から当年予想を再構成せず、「当年予想がどうだったか」の比較は行わない。

## 0.7.2 第2サイクルの固定仮想資金と主KPI — v1.6.1

第2検証サイクルでは、実購入の財布事情と戦略性能を分離するため、`30_betting.md` 0.20の検証用固定仮想資金を使用する。

### 正式な検証母集団

- レース単位：買い判定は10,000円、見送りは0円
- 日次単位：購入優先度上位最大5レース、最大50,000円
- 見送りレースの強制10,000円案は反実仮想として別集計し、正式ROIへ含めない
- 実購入成績は別帳簿とし、検証用仮想成績と混合しない

### 主KPI

第2サイクルの主KPIは次の7項目とする。

1. **日次上位5レース仮想ROI**  
   `日次上位5の総払戻 ÷ 日次上位5の総投資 × 100`
2. **全買い判定レース10,000円固定ROI**  
   日次上位5に入らなかった買い判定も含む。
3. **選別リフト**  
   `日次上位5ROI - 全買い判定ROI` の百分点差。正なら購入優先順位付けが付加価値を出したとみなす。
4. **本線成立時ROI**  
   本線買い目が1つ以上的中したレースだけを対象に、`総払戻 ÷ 総投資 × 100` を集計する。併せて本線成立時に総払戻が総投資を上回った割合も補助記録する。
5. **トリガミ率**  
   払戻が発生したレースのうち、`0 < 払戻 < 投資額` だった割合。本線的中トリガミと押さえのみ的中トリガミを分離する。
6. **予想確信度A/B/C/D別予想精度**  
   各区分で◎勝率・◎複勝率・上位3頭勝ち馬捕捉率・仮想ROIを記録し、特に予想精度が概ね `A > B > C > D` の順になるかを確認する。ROIの単調性は必須としない。
7. **購入判断変更級オッズ誤差率**  
   予測最終オッズと実際の最終オッズの差により、同じ推定確率を用いた買い/見送り判定が反転するケースの割合を記録する。

### 診断用指標

主KPIだけで原因を断定せず、必要に応じて次を補助集計する。

- 予測勝率キャリブレーション / Brier Score
- 見送りレース反実仮想ROI
- 券種別ROI
- ◎勝率・連対率・複勝率
- 最大ドローダウン
- 最大連敗数
- 日次プラス率
- 本線への資金比率
- 予測最終オッズの中央値絶対誤差・相対誤差

単一の高配当的中だけでルールを昇格させず、予想・選別・券種・資金配分・価格予測のどの層が改善または悪化したかを分離して判断する。

## 0.8 「追加」より「統合・置換」を優先する

新しいルールを正式化する場合、必ず次を確認する。

> この新ルールは、既存のどのルールを置換・統合・限定するのか？

既存ルールと同じ目的を持つ場合は、新番号を増やすより既存項目へ統合する。

新しい確認項目が既存ルールの言い換えにすぎない場合は追加しない。

基本予想を肥大化させないこと自体を、予想精度管理の一部とする。

## 0.9 検証中ルールの昇格・降格基準

新仮説は次の順で扱う。

**改善候補 → 検証中ルール → 条件別補正 → 基本予想**

### 改善候補 → 検証中ルール

少なくとも、

- 失敗の原因を説明できる
- 事前に観測可能な情報を使っている
- 結果を知った後だけ成立する説明ではない

ことを確認する。

### 検証中ルール → 条件別補正

原則として、複数の独立したレース・条件で有効性を確認する。

目安として、**5件以上の適用例かつ複数条件**を集め、明確な悪化傾向がないことを確認する。

### 条件別補正 → 基本予想

基本予想への昇格は例外的に扱う。

目安として、**20件以上の適用例**または十分な長期サンプルで、異なる競馬場・クラス・条件でも有効性が確認できる場合に検討する。

有効性が限定条件だけなら基本予想へ上げず条件別補正に留める。

### 降格・廃止

- 効果が確認できない
- 適用条件が曖昧
- 既存ルールと重複
- 予想を不必要にフラット化する
- 情報コストに対して改善幅が小さい

場合は降格または廃止する。

## 0.10 改善仮説ログを原本更新と分離する

各レース回顧では、原本を直接書き換える代わりにまず改善仮説ログへ記録する。

最低限、

- 仮説名
- 発生レース
- エラー分類
- 改善したい判断
- 適用条件
- 期待する効果
- 基本予想との差
- 結果
- サンプル数
- 採用 / 継続検証 / 棄却

を残す。

原本更新は検証サイクル終了時にまとめて行う。

## 0.11 予想の「鋭さ」を監視する

予想精度だけでなく、評価が不必要にフラット化していないかを確認する。

記録候補：

- 勝率1位と2位の差
- 勝率1位と中央値の差
- 上位3頭への勝率集中度
- 予想確信度
- 実際の勝ち馬の事前順位

ただし「差を大きくすること」自体を目的にしない。

長期的に、

- 予想確信度Aなのに確率が極端に平坦
- 予想確信度Cなのに1頭へ過度に集中

などの不整合を検出するために使う。

## 0.11.1 合理的切りと見落としを分離する — v1.6.0

結果として好走した馬を買い目から外していた場合でも、**外したという結果だけで改善候補へ追加しない。**

回顧では次に分類する。

- **合理的切り**：事前情報・確率・役割・券種構造から切る判断が合理的だった → 改善しない
- **想定外要素が上回った**：合理的に低確率としたシナリオが発生した → 記録のみ
- **重要材料の見落とし**：事前に確認可能な強い材料を取得・評価できていなかった → 改善候補
- **資金配分による不採用**：評価はしていたが券種・予算の最適化で切った → 購入層の検証
- **価格だけで無理に拾った / 切った**：印と役割を崩した → 購入判断の検証

上位予想が明確なレースで下位馬を合理的に切ることは、予想の鋭さを保つための正常な判断になり得る。外れた馬を後付けで拾う方向へルールを拡張しない。

## 0.11.2 予測オッズ精度を独立検証する — v1.6.0

オッズ予測は予想能力と分離して継続改善する。可能な範囲で、

- 予測最終オッズ
- 予測時刻
- 実際の購入時オッズ
- 最終オッズ
- 人気順位

を保存する。

単純な平均誤差だけでなく、**購入判断を変えるほどの乖離**を重点的に記録する。特に人気上位、10〜30倍程度の中穴、重賞/平場、予測から発走までの残り時間などで誤差傾向を分けて検証する。

オッズ予測誤差を理由に過去のProduction能力順位を書き換えず、E-08等の価格予測ロジック側の改善材料として扱う。

## 0.12 本バージョンの運用方針

v1.6.1では、**予想ルール追加の速度より、既存ルールと検証プロトコルの有効性測定を優先する。**

当面は、

1. v1.6.1を第2検証サイクルの基準運用ファイルとして運用し、予想生成骨格とv1.6.0購入規約を維持しつつ、予想確信度4段階・固定仮想資金・主KPIを前向き適用
2. 予想生成の基本骨格はv1.4系〜HF1を維持し、正式な購入・監査ガードはv1.6.0を現行優先とする
3. 条件別補正を条件付きで適用
4. Shadow比較予想をProduction固定後に差分記録
5. 基本予想と最終予想を比較
6. 原則2週間・最大約144Rを1サイクルとして集計
7. 第2サイクルではv1.5.0昇格項目の再現性・非劣化と、v1.5.1で追加した検証中ルールの差分価値を重点確認
8. 十分な再現性がなければ追加昇格せず据え置く

という運用を標準とする。

**回顧は毎レース行ってよいが、回顧と原本改訂を同義にしない。** 回顧で得た気付きはまずログへ保存し、サイクル終了時にまとめて検証する。

## 0.12.1 第1検証サイクル終了審査 — v1.5.0昇格判断

> **履歴注記（v1.6.0）**：本項はv1.5.0当時の昇格判断を保存する履歴である。購入義務・券種構造・妙味軸等について本項とv1.6.0が衝突する場合、`30_betting.md`のv1.6.0正式運用（32、35.2、35.3、45.1、48.1）を優先し、本項を現行ルールとして再適用しない。

第1検証サイクルでは、予想生成の基本骨格よりも**最終順位の動かし方・買い目候補生成・妙味馬への依存・購入監査**に同型の失敗が繰り返された。

そのためv1.5.0では、予想生成の能力評価ロジックを大幅に変更せず、以下を優先順位順に正式化する。

### S：正式ルールへ昇格

1. **自然な組み合わせ監査 / 自然な組み合わせ監査**
   - 最終印・確率・主要シナリオから自然に生じる馬連・ワイド・三連系候補を、価格で削る前に一度生成する。
   - ◎○の馬連・ワイドは購入義務ではなく**候補生成義務**とする。
   - 三連系を買う場合、◎○2頭軸だけで終了せず、印内の自然な別組み合わせも監査する。

2. **最終順位保全 / 最終順位保全**
   - 朝・事前基本予想で複数の独立根拠から高評価した馬を、弱い直前情報やオッズだけで大幅降格させない。
   - 大幅変更には強い客観的新情報、または複数の独立材料を要求する。

3. **妙味馬は必須軸ではない / 妙味馬は万能軸ではない**
   - 「最も買いたい馬」と「全券種の共通軸」を分離する。
   - 妙味馬の価値は単勝・複勝・ワイド等で直接買えるため、価格差だけを理由に全買い目をその馬へ依存させない。

4. **万能軸・馬依存監査**
   - 購入前に馬依存率・シナリオ依存率を確認する。
   - 1頭が飛ぶと全買い目が消える構造は、対象馬の好走確率・確率レンジ・予想確信度で明示的に正当化できる場合だけ許容する。

5. **買い目期待値独立評価**
   - 「ある馬同士の馬連が安い」ことを、ワイド・三連複・三連単など別券種の低い期待値根拠へ横滑りさせない。
   - 券種・組み合わせごとに独立して確率と価格を比較する。

6. **良好部分保全 / 非劣化ガード**
   - 回顧で正常に機能した階層を保護し、失敗した階層だけを改善する。
   - 変更案には「何を変えないか」を必ず含める。

### A：正式運用へ統合するが、数値基準は固定しない

8. **①＋②の主従明示**
   - ①＋②と分類したレースは、購入前に必ず「①主＋②従」「②主＋①従」「①≒②」のいずれかを明示する。
   - ①≒②は双方が独立に高い期待値と説明できる場合に限定する。
   - 「①＋②だから半々」の機械配分は禁止する。具体的比率は次サイクルで継続検証する。

9. **公式最新情報優先ルール**
   - 馬場・馬体重・オッズ等の時点情報は、可能な限りJRA等の公式一次情報の最新タイムスタンプを基準にする。
   - 外部サイトと不一致の場合、時刻差を確認せず上書きしない。

### 継続検証中ルール

- **E-08 最終オッズ予測**：運用価値は確認できたが、サンプル不足のため実戦検証中ルールを維持する。
- **E-03 最終価格再確認**：E-08を標準とし、時間に余裕がある場合だけ追加確認する。
- **E-04 位置取り主導権**：有望だが適用例不足。
- **E-07 高確信度活用**：高い予想確信度を連系へ変換する考え方は継続検証。
- **①＋②で原則①主とする仮説**：数例で有効だったが固定ルール化しない。
- **長距離ハンデ・予想確信度B-以下の自動降格**：継続観察。
- **◎の鋭さ／○との順位差**：候補抽出に比べ◎順位が弱い傾向を継続測定し、現時点では予想生成の基本骨格を変更しない。

## 0.14 2週間検証サイクルの記録規約

2週間単位の検証では、**購入したレースだけでなく、事前予想を行ったすべてのレースを記録対象**とする。見送りもレース選別能力を評価する重要な結果として保存する。

### 0.14.1 発走前不変snapshotを回顧の一次証跡とする — 2026-09-21以降

2026-09-21以降に新規固定する第2サイクル対象では、`00_core.md` の契約に従い、正式Production・固定買い目・適用Shadowの発走前状態を `docs/validation/snapshots/YYYY-MM-DD.md` へ保存する。

回顧時の参照優先順位は、

1. **発走前Git snapshot**
2. 同内容を送信したチャット回答
3. その他の結果確認前に固定された事前記録

とする。

発走前Git snapshotに存在しないID・順位・確率・変更理由・買い目・Shadowを、結果後に追加して「発走前保存済み」と扱ってはならない。

`PRE_RACE_SNAPSHOT_PERSIST_FAILED` が発生した場合、予想回答は有効なユーザー向け出力として扱えるが、**Git永続化を必須とする当該KPIについては不適格**とする。Shadow保存失敗だけでProductionを不適格にしないなど、KPI別独立判定は維持する。

回顧では、snapshotの件数・`race_id`・`baseline_forecast_id`・snapshot参照先を最初に取り込む。完了判定は件数だけでなく、次をすべて満たすことを要求する。

- `prediction_scope_count` と対象 `race_id` の**集合**が一致する。
- 対象 `race_id` の重複が0件である。
- 各recordが参照する発走前 `snapshot_id` / baselineが正規参照先で読戻せる。
- 実購入を計上する場合、購入明細の金額合計が記録した実購入総額と一致する。不一致を推測補完しない。

いずれかが不一致なら `REVIEW_SCOPE_MISMATCH` または該当する未確認状態とし、`REVIEW_COMPLETED` として扱わない。

### 0.14.2 2026-09-20以前の既存記録

2026-09-20以前のレースは当時の契約を適用し、発走前チャットsnapshotまたは同等の非チャット事前記録から適格性を判定する。新契約を過去へ遡及適用しない。

正式な検証サンプルに含める条件は、原則として**レース結果を確認する前に必要項目が当時の契約に従って固定され、回顧時に追跡できること**とする。結果確定後に馬柱から再構成したバックテストは参考資料として分離し、前向き検証の成績へ混ぜない。

各レースで最低限、次を回顧時の永続記録へ保存する。

- 日付・競馬場・R・レース名
- 予想時刻と使用できた情報の時点
- 午前モード / 午後当日実測補正モード
- 基本予想上位3頭と基本予想勝率
- 予想を決めた3大要因
- 使用した条件別補正
- 条件別補正 / 検証中ルールによる変更理由と変更量
- 最終上位3頭と勝率・連対率・3着内率
- 初期予想確信度 / 基準予想の予想確信度 / 最終時点の予想確信度
- 予想確信度変更がある場合：変更段階数・理由コード・証拠強度・情報時刻
- 購入確信度（市場未取得・見送り前提なら未判定可）
- 購入優先度（モード2対象時）
- ① / ② / ①＋② / 見送り
- 最も勝つと思う馬 / 最も買いたい馬
- 買い条件・推奨買い目・資金比率
- オッズ取得時刻
- 結果・払戻
- 基本予想 / 条件別補正 / 検証中ルール / 価格判断 / 馬券構造の採点
- エラー分類
- 検証候補の有無
- E-09馬個体適性の主要根拠・証拠強度・比較用差分
- 古馬混合戦ではE-10対象馬と構造的優位差分
- E-12 人気構造タイプ
- E-11集中モード適用可否・本線ワイド基準額額・◎依存率
- 基準買い目 / 検証中ルール比較用買い目の比較

同一レースを複数回予想した場合は、**最初に発走前固定した基本予想**と**発走前最後に固定した最終予想**を両方残す。検証上、結果に対する最終成績は発走前最後の最終予想を使用し、当日実測補正の有効性評価には最初の基本予想との差を使用する。

## 0.16 改訂判定の3段階

サイクル回顧で見つかった問題は、次の3段階に分類する。

### A. 緊急修正

- データ取得の明確な誤り
- 数式・確率の論理矛盾
- 同一根拠の明確な重複適用
- ファイルの運用不能につながる欠陥

結果の当たり外れとは無関係に修正可能とする。

### B. 検証候補

- 同一サイクルで複数回観測
- 発走前に取得可能な情報で説明できる
- 理論的にも再現可能性がある

次サイクルで再現確認する。基本予想は変更しない。

### C. 継続観察

- 1〜2例のみ
- 確率的敗戦で説明できる
- 結果を知った後でしか説明できない

ルール候補へ昇格させない。

## 0.16.1 良好部分保全 / 非劣化ガード（基本運用規約）

サイクル終了審査・毎レース回顧の双方で、改善案は**失敗した階層だけに局所化**する。

必ず、

- **保護**：正常に機能したため変更しない
- **再検証**：有効性が不明で次サイクルでも比較する
- **改善対象**：同型エラーが再現し、変更候補とする

を分ける。

正式な変更案には、

1. 何を改善するか
2. どの事前情報で改善可能か
3. 何を変えないか
4. 既存成功例を壊さないか

を明記する。

単発の失敗で正常機能を弱体化させず、単発の成功で新ルールを昇格させない。

# 40. レース後のエラー分類

# 42. 予想・価格判断・馬券結果を別々に採点する

## 予想面

- 能力評価
- レース質
- ペース

- 成長
- 操縦性・精神面の実戦再現性

- フェアオッズ
- 買い条件
- 実際の購入時オッズ
- 最終オッズ
- オッズ取得時刻・出典の正確性

## 馬券面

- 券種
- 資金配分
- 買い目数
- 高い期待値馬の取り扱い

- 払戻・収支

を分けて検証する。

# 更新ルール

本原本の更新は、今後「毎レース追加型」ではなく**2週間検証サイクル型**で行う。

1. **基本予想ロジックは原則2週間・最大約144Rの1サイクル中は固定する**
2. 1開催日最大36Rを目安とするが、正式サンプル数は実際に結果前予想を保存できたレース数とする
3. 第1サイクルは問題発見、第2サイクルは再現確認、第3サイクル（第3サイクルを通常2週間とした場合、累計最大約468R）は改訂必要性の総合審査を主目的とする
4. **サイクル終了ごとに必ず更新せず、変更の必要性を審査する**
5. 個別レースから得た改善はまず改善仮説ログへ入れ、原本へ即追加しない
6. 新仮説は原則検証中ルールから開始する
7. 検証中ルールを正式化する前に、基本予想との比較を行う
8. 新ルール追加時は、既存のどのルールを統合・置換・限定するかを必ず記録する
9. 該当条件が限定されるルールは条件別補正に留め、全レース共通基本予想へ昇格させない
10. 検証中ルール→条件別補正は原則5件以上かつ複数条件の実戦例を最低目安とし、2週間サイクルをまたいだ再現性を重視する
11. 条件別補正→基本予想は原則20件以上または十分な長期サンプルでの安定性を確認し、可能なら複数サイクルで再現してから検討する
12. 予想を不必要にフラット化する、情報コストが高い、既存ルールと重複する項目は降格・削除する
13. 明確なデータ取得バグ・論理矛盾・重大な運用欠陥のみ、検証サイクル中でも緊急修正を認める
14. 更新時は「追加数」ではなく、**採用・統合・削除・据え置き**をすべて記録する
15. 更新時にはバージョンと最終更新日を変更する

## 更新時の必須レビュー

更新前に、以下を確認する。

- 基本予想の主要原則が以前より埋もれていないか
- 新しい監査項目を能力加点・減点として誤使用していないか
- 同じ目的のルールが複数存在していないか
- 午前予想と午後当日実測補正の成績差はどうか
- 基本予想単独と最終予想のどちらが良かったか
- 検証中ルールが実際に予想を改善したか
- 予想確率が過度にフラット化していないか
- 削除・統合できる項目がないか
- 第1 / 第2 / 第3サイクルのどの段階にいるか
- 前向き検証と結果後バックテストを混在させていないか
- 午前 / 午後の差がサンプル数不足による偶然ではないか
- 市場1番人気など単純なベースラインに対して基本予想が付加価値を出しているか
- ProductionとShadowの決定権が混線していないか
- 51Aの直接事実と51Bの集団傾向が混在していないか
- E-11 / E-12比較案を理由にProduction正式推奨を差し替えていないか
- 同一レース・同一情報時点で別チャットからProduction基準予想を再生成していないか
