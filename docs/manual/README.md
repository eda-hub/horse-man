# 競馬予想ルール — モジュールマニフェスト

- **現行リリース**: `v1.6.1`
- **正本ディレクトリ**: `docs/manual/`
- **履歴管理**: Git の commit / pull request / tag を正本とし、`docs/manual/old/` は作成しない
- **入口**: ルールを利用・編集するときは、最初に必ず本 `README.md` を読む

## 1. 基本原則

このディレクトリの複数ファイルは、独立した文書ではなく**1つの競馬予想ルールシステム**として扱う。

1. 同じ概念を複数ファイルで定義しない。各概念には唯一の Owner を置く。
2. 他モジュールの定義を再掲せず、ルール番号・出力名・モジュール名で参照する。
3. Production は `00_core → 10_prediction → 20_conditional → 30_betting` の一方向で処理する。
4. `40_shadow` は Production 固定後に分岐し、Production へ逆流してはならない。
5. `50_review` は結果後の評価・昇格/降格・変更管理を担当し、当該レースの確定済み Production を遡及変更しない。
6. 必須モジュール間で `manual_release` が一致しない場合、予想・編集を開始しない。

## 3. 依存方向

```text
README
  ↓
00_core
  ↓
10_prediction
  ↓
20_conditional（該当時のみ）
  ↓
30_betting（購入判断時のみ）

Production固定後のみ
10_prediction / 20_conditional ──→ 40_shadow

結果確定後
Production + Shadow + 実購入 ──→ 50_review
```

**逆流禁止**：`30_betting → 10_prediction`、`40_shadow → Production`、`50_review → 過去のProduction` の書き戻しは禁止する。ルール自体の正式昇格は、`50_review` の審査を経た次回PRでのみ行う。

### チャット予想の優先度A実行最適化契約 — 2026-09-18

チャットでの事前予想・最終予想は、**予想品質を変えずにクリティカルパスを短縮する**。以下は実行方法の最適化であり、能力評価・確率・印・買い目の判断基準を変更しない。

1. **分析途中ではGitへ書き込まないが、正式snapshot固定時だけ最小記録を発走前に永続化する。** 事前予想・最終予想・買い目を考えている途中の取得ログ、思考過程、未確定案はGitへ保存しない。Production順位・確率・確信度、必要な購入前監査、固定買い目等が確定したら、ユーザーへのチャット送信直前に `00_core.md` の発走前不変snapshot契約に従って `docs/validation/snapshots/YYYY-MM-DD.md` へ最小snapshotを追記し、同じ内容をチャットへ送る。結果後の正式回顧・KPI集計は従来どおり回顧時に `docs/validation/records/` へ保存する。
2. **静的情報と動的情報を分離する。** 血統、過去走、コース形態、過去のレース傾向など短時間では変化しない情報は `static_evidence_snapshot` として同一レース内で再利用する。取消・騎手変更・馬場・天候・当日馬体重・オッズ・当日バイアス等は `dynamic_evidence_snapshot` として必要時点で更新する。
3. **ProductionとShadowで取得結果を共有する。** 同一の事実データは `race_evidence_bundle` として一度だけ取得・正規化し、ProductionとShadowの双方が参照する。Shadowのために同じ血統・過去走・枠・騎手・厩舎等を再取得しない。
4. **独立取得は可能な限り並列化する。** 実行環境が対応する場合、相互依存しないmanual/Git読込、一次情報、血統・過去走等の外部取得は並列に行う。先行結果が必要な処理、同一ファイルへの書込、Production固定後でなければ開始できないShadow判断は順序を守る。
5. **同一レースの既存Productionを再利用する。** 同じ `manual_release`・同じレースで有効な `baseline_forecast_id` があり、強い非価格情報による正式更新条件を満たさない場合、Productionをゼロから再生成しない。最終予想では既存の静的snapshotとProductionを基礎に、動的情報と影響箇所だけを差分更新する。

取得済み情報に時刻・出所・対象範囲があり、現在も有効と判断できる場合は再取得を目的化しない。逆に、取消・馬場・馬体重・オッズ等の時点依存情報は古いsnapshotを最新値として扱わない。

### JRA当日馬体重取得契約（チャット予想）

JRAの発走当日予想、直前予想、最終予想では、**当日馬体重を単なる「確認できれば使う情報」にせず、取得を必ず試行する必須一次情報**として扱う。出力を簡潔にする指定があっても、内部の取得試行を省略しない。

#### 適用範囲

本節は、ChatGPT上で予想ルールを実行するときの**情報取得行動だけ**を定義する。

- ローカルシステムのAPI、イベント監視、DB、polling、保存形式、再起動復旧等の実装方式は定義しない。
- チャット実行時に、ローカルJV-Link実装が存在・稼働しているものとして扱わない。
- 実際に接続された取得経路がない限り、チャット側でJV-Linkから取得したと表現しない。
- 将来コード実装の正本は `DECISIONS.md` と `docs/jravan/` とし、本 `docs/manual/` へ実装詳細を書き戻さない。

#### チャットでの取得タイミング

- 当日馬体重は発走20分前になってから初めて探すものではない。
- 発走当日に対象レースの予想依頼を受けた時点で、その時点の当日馬体重取得を試行する。
- まだ未発表と判断できる場合を除き、最終予想では再確認する。
- 固定の「発走○分前なら必ず取得可能」という前提を置かない。

#### チャット / Webでの取得手順

1. JRA公式の当日出馬表・詳細出馬表等の一次情報から、対象レースの当日馬体重と前走比を取得する。
2. JRA公式で全頭分を取得できない場合は、**スポーツナビを第一フォールバック**として、下記の取得タスクを実行する。スポーツナビも利用不能な場合は、最終予想の締切内で当日更新される他の信頼できる競馬情報源を確認する。
3. 静的HTML・検索index・検索キャッシュで空欄だったことだけを理由に「未発表」と断定しない。利用可能な別の取得経路を少なくとも1回確認する。
4. JavaScript描画後のライブ値を確認できない実行環境では、その制約を明示し、取得できたふりをしない。
5. 調教後馬体重・前走馬体重を当日馬体重として代用しない。

#### スポーツナビでの馬体重取得タスク

1. [スポーツナビ競馬トップ](https://sports.yahoo.co.jp/keiba/)の開催一覧、または「日程・結果」から、対象の開催日・競馬場を選び、対象Rの「出馬表」を開く。確認したリンクを辿り、レースIDやURLを推測して組み立てない。
2. 開いたページの**開催日・競馬場・R・発走時刻**をJRA公式で確認した対象レースと照合する。不一致の場合はそのページの値を採用せず、対象レースを選び直す。
3. 出馬表本文の**馬番・馬名・当日馬体重・増減**を取得し、JRA公式で確定した現在の出走対象馬と対応付ける。検索結果の抜粋、前走情報、競走馬の過去成績を当日値の取得済み根拠にしない。
4. 取消・競走除外済みを除く全対象馬について取得頭数 / 対象頭数を照合する。`-(-)` や空欄は未取得、数値の `0` は増減なしとして区別し、欠測を0で補完しない。馬体重のみ取得できて増減が確認できない場合も、その不足を明示する。
5. **取得元URL・こちらの取得時刻（JST）・ページ表示の更新時刻（あれば）・取得範囲・未取得馬と理由**を実行コンテキストへ保持する。ページの更新時刻は馬体重の発表時刻と同一とは限らず、表示がなければ不明とする。
6. JRA公式でも値を取得できている馬は照合し、矛盾があれば公式を優先する。公式が未取得のまま代替値を使う場合は、スポーツナビ由来で公式の数値との照合は未完了と明示する。
7. 空欄や古い表示しか取得できない場合は、未発表と断定せず、下記「取得結果の扱い」と「時間制約付き情報取得のfail-soft原則」に従う。スポーツナビを必須依存にして再試行を続けない。

本タスクは馬体重の取得に限定する。同じ出馬表に表示される人気・オッズを、オッズ確認前の能力評価やProduction基準順位の根拠へ混入させない。

#### 取得結果の扱い

取消・競走除外済みを除く現在の出走対象馬について、当日馬体重と増減が全頭分揃っているか確認する。

- 全頭取得できた場合は、取得元・取得時刻・全頭取得済みであることを保持する。
- 一部だけ取得できた場合は、取得できなかった馬を明示する。
- 発表済みと考えられるのに利用可能な取得経路から取得できない場合は、**取得経路障害**として扱う。
- 取得できないまま最終予想を作る場合は推測で補完せず、馬体重未取得を明示し、情報不足として予想確信度・購入確信度へ反映する。

本節は**チャット予想時に馬体重取得を必須工程として実行するための契約**であり、馬体重そのものの評価方法や加減点、将来のローカルシステム実装方式を定義するものではない。

### 時間制約付き情報取得のfail-soft原則

発走前予想は**締切のある処理**として扱い、補助的な取得経路・外部サービス・追加分析を待ち続けて予想自体を発走に間に合わせられなくすることを禁止する。

- 主催者公式・一次情報など重要度の高い取得を先に試行する。
- 代替ソースや補助サービスは非ブロッキングとし、応答が遅い・不安定・利用不能なら再試行を打ち切る。
- 単一の外部サービス、プラグイン、ブラウザ経路等を、最終予想を出すための必須依存にしない。
- 最終予想固定に使える時間内に取得できなかった情報は、推測で埋めず「未取得 / 取得経路障害」と明示し、必要に応じて予想確信度・購入確信度を下げたうえで利用可能な情報だけで処理を完了する。
- 情報取得のために最終予想が発走時刻を越えた場合、その出力を発走前Productionとして後から保存・前向きKPIへ算入しない。

この原則は特定のサービス名に依存せず、今後取得手段が変わっても適用する。

### 重賞の年次予想ノート運用

JRA重賞は原則として全レースを予想対象とし、「見送り」は購入判断として扱う。

JRA・海外を含む重賞の `docs/yosou/` 保存境界は `docs/yosou/README.md` を唯一の共通Ownerとする。JRA固有の補足は `docs/yosou/jra_racing/README.md`、海外固有の補足は `docs/yosou/kaigai/README.md` に置く。

重賞の結果確定後は、**Production / Shadowの正式回顧、KPI、エラー分類、実購入、反実仮想、非劣化判定等を `docs/validation/` に保存し、`docs/yosou/` へ重複保存しない。** `docs/yosou/<区分>/<race>.md` には、過去傾向から見た当年予想・結果の照合、傾向の継続 / 弱化 / 新規候補 / 例外、翌年に向けたレース固有の予想課題だけを残す。

### 検証データ・正式回顧の保存場所

進行中の検証サイクルで生成するProduction / Shadowの結果後評価、実購入記録、エラー分類、KPI、比較差分・集計は、ルール定義とは分離して `docs/validation/` に保存する。`docs/validation/` は**現行サイクル専用の一時領域**であり、ルールの正本ではない。サイクル終了時に必要な昇格・降格判断を `50_review.md` の手順で確定した後、当該サイクルの検証ファイルは削除し、過去状態はGit commit / pull request / tagから参照する。

重賞の `docs/yosou/` は検証データの保存先ではない。正式回顧をvalidationへ保存した後、翌年用のレース固有知識だけを抽出して更新する。

## 5. 編集時の読み込み規約

変更対象モジュールの内部ロジックだけを変更し、`produces` / `depends_on` / `must_not_modify` を変えない場合は、原則として次だけ確認する。

- `README.md`
- 対象モジュール
- 対象モジュールが依存する上流モジュール

一方、モジュール間インターフェース、出力名、Production/Shadow境界、優先順位を変更する場合は、**直接依存する下流モジュールも必ず確認する**。

変更PRでは最低限、次を確認する。

- 同一概念の重複定義を追加していないか
- Ownerが変わる場合、旧Owner側の定義を削除したか
- ルール番号を不用意に変更していないか
- ProductionとShadowの逆流が発生していないか
- 必須モジュールの`manual_release`が一致しているか
- 良好部分保全 / 非劣化ガードに反していないか

## 6. 共通受け渡しキー

モジュール間では、少なくとも次を同一レースの共通キーとして扱う。

- `baseline_forecast_id`（基準予想ID）
- レースID / 開催日 / 競馬場 / R
- 情報取得時刻
- Production基準順位・確率・予想確信度
- 使用オッズ時刻（買い目作成時）

JRA当日・最終予想では、取得できた場合はさらに当日馬体重の取得元、取得時刻、取得範囲（全頭 / 一部）を同一レースの実行コンテキストへ保持する。

同じレースに既存のProduction基準予想IDがある場合、強い非価格情報による正式更新条件を満たさない限り、新しいProductionをゼロから作らない。あわせて、同一レース内で取得済みの `static_evidence_snapshot` を再利用し、更新が必要な `dynamic_evidence_snapshot` とその影響範囲だけを再評価する。Production / Shadowは同一の `race_evidence_bundle` を参照し、同じ事実データを別々に再取得しない。

## 7. ルール番号と履歴

分割後も既存の `0.x`、`1〜51`、`E-xx` の番号を維持する。過去の予想・回顧から追跡できることを優先する。

旧版をファイルコピーで残さず、過去状態はGitのcommit / PR / tagから取得する。

## 8. GitHub運用

- 現行ルールの参照は原則として `main` の `docs/manual/README.md` から開始する。
- 重賞の年次予想ノート運用は `docs/yosou/README.md` を共通正本とし、JRA / 海外の区分別READMEはその補足とする。
- 改訂は作業ブランチで行い、pull requestの差分レビュー後に `main` へ統合する。
- チャットでの事前予想・最終予想そのものは改訂作業ではない。分析途中のGit書き込みは禁止する一方、**発走前に正式固定した最小snapshotだけは検証証跡として `docs/validation/snapshots/` へ保存する。** これはルール改訂ではなくappend-onlyの検証データ記録であり、詳細な結果・回顧・KPIは結果後に `records/` へまとめる。
- 旧版確認はGitのcommit / PR / tagから行い、`old/`への複製保存はしない。
- ルールの意味を変更しない構造整理・記録運用整理では `manual_release` を維持できる。予想判断・閾値・決定権を変更する場合はリリース更新対象として `50_review.md` の更新規約に従う。
